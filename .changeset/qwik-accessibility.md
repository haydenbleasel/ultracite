The Oxlint and ESLint `qwik` presets now lint Qwik's JSX for accessibility, with the same `jsx-a11y` rules, severities and options as the `react` presets. Until now a Qwik project got no accessibility checks on either linter, because the rules lived in the `react` presets only.

Qwik projects on Oxlint and ESLint will see new errors. Thirty-four rules are on at `error` in each, covering missing `alt` text, labels and controls that aren't associated, anchors with no `href`, invalid ARIA roles and attributes, media without captions, and more. Measured on two open-source Qwik codebases, the rules that report most are `jsx-a11y/control-has-associated-label`, `jsx-a11y/label-has-associated-control` (ESLint), `jsx-a11y/alt-text` and `jsx-a11y/role-supports-aria-props`, and on Oxlint `jsx-a11y/prefer-tag-over-role`.

- The rules that look at event handlers don't work on Qwik's handlers yet. `jsx-a11y/click-events-have-key-events`, `jsx-a11y/mouse-events-have-key-events`, `jsx-a11y/interactive-supports-focus`, `jsx-a11y/no-static-element-interactions` and `jsx-a11y/no-noninteractive-element-interactions` only know React's names, and Qwik's end in `$`, so a `<div onClick$={…}>` with no keyboard handler isn't reported by either linter. They're on anyway: they report nothing wrong on `$` handlers, and they'll start reporting when Oxlint and `eslint-plugin-jsx-a11y` learn the names. On the codebases measured, that would be 46 more reports on ESLint and 37 on Oxlint.
- Qwik writes `class` and `for` where React writes `className` and `htmlFor`. The ESLint preset tells the label rules that a label's target is `for`, so `<label for="email">` beside `<input id="email" />` passes, and a label with no control is still reported. No rule reads `className`.
- On Oxlint, `jsx-a11y/label-has-associated-control` is off. Oxlint only accepts `for` through `settings["jsx-a11y"].attributes`, and it doesn't read `settings` from a preset ([oxc-project/oxc#28047](https://github.com/oxc-project/oxc/issues/28047)), so the rule would report every `<label for="…">`. To turn it on, set `"jsx-a11y/label-has-associated-control": "error"` in `rules` and `"jsx-a11y": { attributes: { for: ["htmlFor", "for"] } }` in `settings` in your own `oxlint.config.ts`.
- On ESLint, a `<Slot />` isn't counted as a label's control the way `{children}` is in React, so a label component that renders `<label {...props}><Slot /></label>` is reported by `jsx-a11y/label-has-associated-control`. Give the label a `for`, or disable the rule on that line.
- `jsx-a11y/no-autofocus` is off, as it is in the React presets, and on ESLint so is `jsx-a11y/prefer-tag-over-role`, which crashes on an object-valued `role` ([jsx-eslint/eslint-plugin-jsx-a11y#1102](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y/issues/1102)).
- `jsx-a11y/anchor-is-valid` and `qwik/jsx-a` both report an `<a>` with no `href` on ESLint.

`ultracite init` installs `eslint-plugin-jsx-a11y` for Qwik projects that choose ESLint. Existing projects get it from `ultracite upgrade`, which installs every plugin the presets in your ESLint config load, and `ultracite doctor` reports it as missing until then. Oxlint's rules are built in, so there's nothing to install. Biome's accessibility rules already run from its core preset, so it doesn't change.
