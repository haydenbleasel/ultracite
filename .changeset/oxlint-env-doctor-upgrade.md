`ultracite doctor` now warns when an `oxlint.config.ts` extends the core preset without setting `env`, and `ultracite upgrade` adds it. Oxlint doesn't inherit `env` through `extends` ([oxc-project/oxc#20087](https://github.com/oxc-project/oxc/issues/20087)), so a config `init` wrote before 8.0.1 lints without the browser and Node globals, and `no-implied-eval` misses `setTimeout("code")` and `no-eval` misses `window.eval`, with nothing to say so. `upgrade` makes the change through the same update `init` runs, so the rest of the config is kept as written. A project that still has an `.oxlintrc.json`, or a config `init` can't update, is left for `ultracite init`, and `upgrade` only says it added `env` when it did. When the config takes core through a name of its own (`const base = { ...core }`) or imports a preset with `import * as`, `doctor` says to add `env` by hand, and when the config is in a parent directory it says where to run `upgrade`. A config that spreads in another object (`...shared`) may set `env` through it, so `doctor` says it can't tell rather than that `env` is missing, and `upgrade` leaves it alone instead of moving the spread among the properties it writes. A config `doctor` can't read, or one the Oxlint configuration check fails on (next to another Oxlint config, or a `.ts` config in a CommonJS package), gets no `env` check rather than a pass.
