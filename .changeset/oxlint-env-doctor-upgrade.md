`ultracite doctor` now warns when an `oxlint.config.ts` extends the core preset without setting `env`, and `ultracite upgrade` adds it. Oxlint doesn't inherit `env` through `extends` ([oxc-project/oxc#20087](https://github.com/oxc-project/oxc/issues/20087)), so a config `init` wrote before 8.0.1 lints without the browser and Node globals, and `no-implied-eval` misses `setTimeout("code")` and `no-eval` misses `window.eval`, with nothing to say so. `upgrade` makes the change through the same update `init` runs, so the rest of the config is kept as written. A project that still has an `.oxlintrc.json`, or a config `init` can't update, is left for `ultracite init`, and `upgrade` only says it added `env` when it did. When the config takes core through a name of its own (`const base = { ...core }`), imports a preset with `import * as`, or declares a name the Ultracite config also declares (its own `jsPluginSettings`, say), `doctor` says to add `env` by hand and why `upgrade` can't. When the config is in a parent directory, it says where to run `upgrade`. A config that spreads in another object (`...shared`) may set `env` through it, so `doctor` also says it can't tell. A config `doctor` can't read, or one the Oxlint configuration check fails on (next to another Oxlint config, or a `.ts` config in a CommonJS package), gets no `env` check rather than a pass.

`ultracite init` and `upgrade` no longer move a spread in an Oxlint config. `init` writes `env`, `extends`, `ignorePatterns`, `jsPlugins` and `settings` ahead of everything it carries over, so a spread that came before one of them ended up after it and overrode it. Such a config is now left unchanged, with a warning that says what to move. A spread after those properties stays where it is, and a property `init` adds goes ahead of it, so whatever the spread sets still wins. `init` also no longer says it updated the Oxlint config when it left it unchanged.
