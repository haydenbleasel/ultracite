# TODO comments in real TypeScript codebases: measurement report

The data behind the post on TODO comments and self-admitted technical debt, measured on 2026-10-18. Generated tables are in `tables.md`. The machine-readable results are:

- `inventory.json`: the rules per linter and preset, with options, defaults and fix kinds, and the Biome checks
- `comment-census.json`: every task marker in the corpus, per repo and pooled
- `rule-census.json` and `rule-census.md`: the Oxlint census
- `linters.json`: the calibration matrix with every message and help text, and what each fix pass does
- `corpus-lint.json`: the four rules on the corpus in every configuration, which markers each catches and why it misses the rest
- `markers.json`: each repo's own lint configs, disable comments, and markers next to suppressions
- `issues.json` and `stale-check.json`: linked issues and the hand check of the closed ones
- `history.json`: age at the pinned commit, survival, and how markers were removed
- `sample.json`, `removal-sample.json` and `classifications.json`: the two hand classifications, both raters
- `agent-runs.json`: markers in the agent experiment's own committed runs
- `decision-history.json`: how Ultracite came to turn these rules on

The agent-experiment subjects are in `corpus/examples/todo-comments/`. Everything is regenerated by `research/corpus/scripts/todo-*.cjs` (see §11).

Terms used throughout:

- **Task marker:** TODO, FIXME, XXX, HACK, BUG, NOTE, OPTIMIZE, REVIEW, TBD, "to do" or the JSDoc `@todo` tag, written as a tag. That means in capitals, followed by `:` `(` `[` or a dash, or opening its comment. TODO, FIXME and TBD count in any case. "Note that…" and "a bug in Safari" are prose; `foo.xxx` and `{XXX}` are embedded. The exact rules are in `comment-census.json` `definitions`.
- **Rule terms:** TODO, FIXME and XXX, the default terms of `no-warning-comments` and `unicorn/expiring-todo-comments`. **TODO-family** adds `@todo`.
- **Bare:** a marker with none of these:
  - an owner: a person named as `TODO(name)`, `TODO@name` or an `@mention` of a commit author
  - a link: an issue or PR, a URL, a tracker key
  - a date, a version, or a condition to wait for

## TL;DR

- **Corpus.** The same 8 codebases, SHAs and 3,333 files (694,309 lines, 53,259 comments) as the earlier reports.
  - Ultracite's own CLI is listed separately.
  - The four React codebases the accessibility post added are a separate set: all source files, 449,047 lines, most of them Supabase Studio, the only application in either set.

- **What Ultracite turns on.**
  - **Oxlint's default presets:** `no-warning-comments` (core), with no options: terms `todo`, `fixme`, `xxx`, location `start`, no decoration.
    - The opt-in js-plugins preset adds `sonarjs/todo-tag` and `sonarjs/fixme-tag`.
    - Oxlint has no port of `unicorn/expiring-todo-comments`.
    - `react/todo` in the react preset is unrelated: it reports code the React Compiler can't analyze.
  - **ESLint core:** all four.
    - `no-warning-comments` comes from `@eslint/js`'s `all` config, and the two sonarjs rules with every other sonarjs rule.
    - `unicorn/expiring-todo-comments` runs with unicorn's defaults, which include `allowWarningComments: true` and `checkDates: false`.
  - **Biome:** nothing.
    - None of the 565 rules in Biome 2.5.15's schema is about task markers.
    - `biome explain` mentions a marker word only in two unrelated rules.
    - Biome's rules-sources page maps no Biome rule to any of the four.
  - **None of these rules has an autofix or a suggestion** in any linter.

- **How many TODOs there are.** 882 TODO, FIXME and XXX markers in 880 comments: 12.7 per 10,000 lines, or 1 comment in 60. There are 857 TODOs, 25 FIXMEs, no XXX and 22 `@todo` tags.
  - **Next.js has 679 of them (77%)**, 24.6 per 10,000 lines. The other seven repos have 4.9 per 10,000, from 0 (hono) to 6.5 (Excalidraw). The React set has 2.2 (Supabase Studio 2.0).
  - **Ultracite's CLI has none**: its own config turns `no-warning-comments` on.
  - **Markers are uniform:** 99% are in capitals, 92% open their comment, and 70% are followed by a colon.

- **Most are bare.** 693 of 882 (79%) name no owner, link, date, version or condition (70% without Next.js).
  - 23 name a person: 15 in VS Code (its `TODO@name` convention) and 8 in Next.js.
  - 48 carry a link: 26 to an issue or PR, and 17 a tracker key such as Next.js's `NAR-804`.
  - 28 name a version, and 112 an event to wait for ("once X is released").
  - Next.js tags another 132 with a topic (`TODO(app-shells)`) or an area (`TODO-APP:`).
  - No marker uses unicorn's `[condition]` syntax.

- **What the rules report.** Oxlint and ESLint agree exactly:
  - `no-warning-comments` 808 diagnostics, `sonarjs/todo-tag` 859, `sonarjs/fixme-tag` 25, `unicorn/expiring-todo-comments` 0.
  - No repo turns any of them on in its own config, and no disable comment names one, so raw and reported counts are the same.
  - **Which markers they catch** (of 904 TODO-family markers): `no-warning-comments` 810 (90%), and `sonarjs/todo-tag` 859 of 879 TODOs and `@todo`s (98%). Some rule catches 903.
  - **`no-warning-comments` misses 94,** all because the term isn't at the start of the comment: 41 later in a line comment, 30 in JSDoc blocks, all 22 `@todo` tags (written `// @TODO …`), and 1 after decoration.
  - **`sonarjs/todo-tag` misses 20:**
    - 15 followed by a tracker key. It skips Jira-style keys on purpose, so Next.js's `TODO(NAR-804)` is silent.
    - 4 in `eslint-disable` reasons.
    - 1 `Todo:` at the start of a JSDoc line, which it treats as prose.
  - **Two reimplementations predict the rules exactly**, comment by comment, on the calibration and on the whole corpus.

- **What an agent is told.**
  - **Oxlint:** "Unexpected 'todo' comment: TODO: …", with the help **"Remove or rephrase this comment"**. Oxlint's own docs show `// Note: This explains something` as the correct example.
  - **ESLint:** "Unexpected 'todo' comment: '…'.", with the docs description "Disallow specified warning terms in comments".
  - **sonarjs:** "Complete the task associated to this "TODO" comment." The help in ESLint is 'Track uses of "TODO" tags'; through Oxlint's JS plugin there is none.
  - **Ultracite's prompt says "Restyling the flagged code … will not clear it".** For these rules it does: every rewording in the calibration that drops or moves the word silences `no-warning-comments`.

- **The TODOs are old and mostly still meant.**
  - **Age:** by `git blame` at the pinned commit, the median TODO-family marker line is 506 days old (765 without Next.js). 34% are under a year old and 21% over three.
  - **Hand sample:** 102 markers, with a blind second rater on 36. The shares below are for the eight repos' 89, weighted by repo.
    - **Type**, in Maldonado and Shihab's categories: design 61%, requirement 27%, defect 10%, documentation 2%, test 0 (κ 0.93).
    - **On hold**, waiting for something outside the code at hand: 15% (κ 1.00).
    - **Still valid at the pinned commit:** 81%. 7% no longer apply and 12% can't be told (κ 0.54).
    - **Deleting the comment would lose information a maintainer would want** for 87% (κ 0.82).
    - 54% would change runtime behaviour if done, and 36% could be done inside their own file.

- **What happens to them.** Every marker was followed on each project's mainline, across all eight repos and the measured source directories in every layout they've had.
  - Of 1,892 TODO-family markers added from 2018 to 2024, 1,468 (78%) were gone by the pinned commit.
    - Half are gone within 179 days (Kaplan–Meier), and 16.5% survive five years.
    - Without Next.js: 84% removed, median survival 84 days.
  - **How they went** (automatic, after Zampetti et al.): the enclosing function changed in 53%, the file was deleted in 15% and the function in 12%. In 13% the comment was removed with its code unchanged.
  - **Was the task done?** A hand sample of 89 removals, with a blind second rater on 30 (κ 0.78):
    - addressed 55% (58% weighted to the population)
    - the code was deleted 16%, or rewritten for another reason 9%
    - the comment was deleted as already done 8%, the code moved 6%, and the comment was deleted with the debt still there 6%
    - The removing commit's message mentions the task in 31%.
  - **Who removed them:** the person who added a marker removed it in 51% of cases.

- **Linked issues are rare and mostly open.** 26 of 915 TODO-family markers reference a GitHub issue or PR (17 distinct).
  - 14 markers point only at closed issues or merged PRs. Read by hand, 10 are still valid (the link is context) and 3 are unclear.
  - 1 is stale: Next.js's "Remove from dependencies once react#29665 is released". That PR shipped in React 19.0.0.

- **unicorn's expiring TODOs never expire here.** With the defaults Ultracite uses, `unicorn/expiring-todo-comments` reports no bare TODO and no expired date.
  - Date checks have been off by default since eslint-plugin-unicorn 65; its release notes say the opposite.
  - It reports only bracketed version, package and engine conditions, and malformed ones.
  - The corpus has none, so it fires 0 times.

- **Agents in our earlier experiments wrote no TODOs.**
  - Across 138 committed runs (68 Claude Code, 70 Codex) and 226 agent patches, no marker was added or removed.
  - The agents added 33 comment lines in 14 runs, all of them Claude Code, none of them a marker.
  - No subject contained a marker.

- **Agent-experiment subjects** (§9): three real TODOs, each flagged by Oxlint's `no-warning-comments`, type-checked and with a behaviour oracle.
  - **A, obsolete:** Vite's `handleHMRUpdate` (2021), `// TODO auto restart server`, above code that already restarts the server. The project dropped the word 60 days after the task was done.
  - **B, a known bug:** Vite's `HMRClient.prunePaths` (2024), `// TODO Trigger their dispose callbacks.` vitejs/vite#15782 fixed it upstream, making the method async and changing its callers in two other files.
  - **C, on hold:** Excalidraw's `loadFromJSON` (2026), "Be over-permissive until WebKit bug 34442 gets resolved". It has been kept for 5 years and 7 months, and the bug is still open.
  - **The lint can't tell the edits apart.** On each subject, every edit that deletes, rewords or moves the marker clears `no-warning-comments`, whether it's right or wrong. None of the wrong ones changes behaviour except "doing the task".

## 3. Method

### 3.1 The comment inventory (`todo-census.cjs`)

- **Comments come from typescript-estree** (`comment: true`), the same `comments` array ESLint's `getAllComments()` returns.
  - Strings, template literals, regexes, identifiers and JSX text are never comments.
  - A `{/* … */}` child is marked as a JSX comment.
  - All 3,333 corpus files parse.
- **Every occurrence** of the eleven terms is recorded, case-insensitively, at word boundaries, with:
  - the term, its case, what precedes it on its line (decoration) and what follows it
  - the comment kind
  - its position in the comment:
    - `start`: only whitespace before it (`no-warning-comments`' default location)
    - `start-decorated`: only `*` `/` `!` `#` `=` `+` `-` and whitespace
    - `line-start`: the start of a later line of a block comment
    - `later`: anywhere else
- **The marker's text** is the rest of its comment line, plus the lines that continue it (the following lines of a block comment, or adjacent `//` comments at the same column), up to a blank line or another marker. Its format is read from that text:
  - **`TODO(x)`:** an issue (`#n`, URL), a tracker key (`NAR-804`), a date, a person, or a topic. A person means every word of `x` is a commit author's name, first name, email local part or GitHub login in the history clone. `TODO@name` (VS Code's convention) and `@mentions` of authors are owners too.
  - **Links:** issue and PR references (GitHub URLs, `owner/repo#n`, `#n`), other trackers (crbug, WebKit and Mozilla Bugzilla, Linear), tracker keys (Jira-style, minus common acronyms such as `UTF-8`), and URLs.
  - **Dates and versions:** dates (ISO, `m/d/yyyy`, month and year), and versions (`v1.2`, `x.y.z`, a product and a version such as `React 18`, "next major").
  - **Conditions:**
    - **strict**, an event to wait for: "once X is released", "remove when Y lands", "blocked on Z"
    - **loose**, any of once, when, after, until, unless, pending and similar, which also describe code ("handle the case when x is null")
  - **Other:** unicorn's `[conditions]` right after the term, and area tags glued with a dash (`TODO-APP:`).
- **Spot checks on the first runs tightened three definitions.**
  - An em dash after a lower-case word no longer makes it a marker ("implies a bug — see").
  - Placeholders (`{XXX}`, `next-test-XXX`, `xxx[`) are embedded.
  - Matching commit authors replaced the first owner heuristic, which counted Next.js's topic tags (`TODO(after)`, `TODO(veil)`) as people.

### 3.2 The rules (`todo-inventory.cjs`)

- **Oxlint:** every preset in `config/oxlint`, top level and overrides. `oxlint --rules` gives category, fix kind and whether a rule exists, and Oxlint's `configuration_schema.json` gives the defaults.
- **ESLint:** `calculateConfigForFile` on `.ts`, `.tsx`, `.js` and `.test.ts`, for core, core + react and core + type-aware. These are the options a file actually gets (ESLint 10 materialises defaults). Each rule's meta records fix kind, suggestions, messages and docs.
- **Biome:** every rule in the schema, with the first paragraph of `biome explain` for each, searched for TODO, FIXME, XXX, HACK and "warning comment".
  - Also Biome's own rules-sources page (biomejs/website `src/content/docs/en/linter/rules-sources.mdx` at `de75d6a7`, 2026-08-24), which lists the ESLint and plugin rules each Biome rule comes from. It was fetched with `gh api` and searched for the four rules.

### 3.3 The linters on the corpus (`todo-rule-census.cjs`, `todo-linters.cjs --corpus`)

- **The census** ran core + react + js-plugins over the eight repos and Ultracite, in both modes, focused on the three Oxlint rules and `no-inline-comments`.
- **The corpus run** covers all thirteen repos:
  - Oxlint (default and js-plugins) on the originals (reported), and on a mirror with every `eslint-`/`oxlint-disable` neutralised (raw)
  - ESLint core on the originals, with and without inline config
- **Every diagnostic is joined to its comment** (the file's typescript-estree comments, by line), and then to the marker it reports. `no-warning-comments` reports the comment; sonarjs reports the line of its own term. No diagnostic failed to land on a comment.
- **The matchers.** `todo-lib.cjs` reimplements the rules from their sources:
  - **`no-warning-comments`**, from ESLint 10.12.0: `/^[\s<decoration>]*<term>\b/iu` per term at location `start`.
  - **The two sonarjs rules**, from 4.2.2's `S1135/rule.js`:
    - the pattern anywhere, not next to a letter, one report per line
    - `todo-tag` also skips a TODO followed on its line by a key matching `/\b[A-Z][A-Z0-9]+-\d+\b/`, a `Todo` opening a sentence or the comment, and a lower-case `todo` mid-sentence
    - both skip comments that start with `eslint-disable`
  - For every comment in the corpus, the matchers' count equals each real rule's count, in ESLint and in Oxlint. The miss tables use them to say why a marker was missed.

### 3.4 Calibration (`calibration/todo-comments/`, `todo-linters.cjs --calibration --autofix`)

- **`cases.tsx`** has 77 cases:
  - 37 forms (T01–T37)
  - 14 of unicorn's conditions (U01–U14)
  - 26 rewordings an agent might use to make the rule stop firing (R01–R26)

  Each case starts with a `caseStart("ID", "…")` call rather than a comment, so the headers can't trip the rules.
- **`package.json`** gives unicorn a version (2.0.0), a dependency (`react` ^19.0.0) and an engine (`node` >=20) to compare against.
- **Configurations:** Oxlint default and js-plugins, ESLint core + react raw and reported, and Biome core.
- **Recorded:** every focus diagnostic with its message and the help the handoff carries, and every other comment rule that fires on the same lines.
- **`--autofix`** runs each fix pass `ultracite fix` uses on copies under the system temp directory (the presets ignore `**/out`), and compares each case's comments before and after:
  - `oxlint --fix` and `--fix-dangerously`, with both configs
  - `eslint --fix`
  - `biome check --write` and `--write --unsafe`

### 3.5 Policy and suppressions (`todo-markers.cjs`)

- **Configs:** every ESLint (flat and legacy), Biome and Oxlint config, and `package.json` `eslintConfig`, at each repo's pinned commit.
  - They come from `git ls-tree` and `git show` on the history clone, so Next.js's and VS Code's root configs count although their corpus clones are sparse.
  - Configs for tests, fixtures, examples, project templates and evals are left out, and for Ultracite its presets and research configs.
  - Lines naming a rule are recorded, and so are shared configs that would turn these rules on implicitly (`eslint:all`, unicorn's or sonarjs's recommended sets).
- **Disable comments** naming one of the rules.
- **TODO-family markers next to suppressions:** inside a suppression comment (its reason) or on the line next to one. The suppressions are `@ts-expect-error`, `@ts-ignore`, `@ts-nocheck`, `eslint-disable*`, `oxlint-disable*`, `biome-ignore`, `prettier-ignore` and coverage ignores.

### 3.6 Linked issues (`todo-issues.cjs`, `stale-check.json`)

- **Fetching.** Every GitHub issue or PR a TODO-family marker references was read with `gh api repos/<repo>/issues/<n>` on 2026-10-18, read-only, and cached.
- **State at the pinned commit.** A state is also given at the pinned commit: an issue closed after it was still open then.
- **Candidates.** A marker whose issues are all closed as completed, or merged, is a candidate stale TODO. I read each candidate's code at the pinned commit and its issue, and recorded a verdict (one rater).

### 3.7 History (`todo-history-clone.sh`, `todo-history.cjs`)

- **Clones.** Bare clones of each default branch, under `repos/history/`.
  - The six smaller repos have no blobs over 1 MB.
  - Next.js (2.6 GB on GitHub) and VS Code (1.6 GB) have commits and trees only, then `git backfill --sparse` for the measured source directories:
    - Next.js: its `packages/next` source directories in both layouts, without `compiled/` and `bundles/`
    - VS Code: `src/vs/editor/common`
  - Every pinned SHA is in its clone. Only `git log`, `git blame`, `git show` and `git diff` ran on them.
- **Age:** `git blame --line-porcelain -w -M` at the pinned commit, on the line of each TODO-family marker. The repo's `.git-blame-ignore-revs` is used where it has one (Vite, Astro, Next.js, VS Code). Blame dates the line's last change, so a reformatted or reworded line looks younger than its marker.
- **Survival:** `git log --first-parent --diff-merges=first-parent -M -p -U0` over each package's source directories in every layout it has had, with `collect-files.cjs`'s test, fixture and vendored exclusions.
  - **The layouts:** zod `src` then `packages/zod/src`; Vite `src` then `packages/vite/src`; Astro, Excalidraw and Next.js likewise; tRPC's package sources; hono `src`; VS Code `src/vs/editor/common`.
  - **What counts as a marker line:** TODO, FIXME or XXX in capitals, `todo`/`fixme` opening a comment, or `@todo`, after a comment opener on the line. 873 of the corpus's 882 rule-term markers are in capitals.
  - **Tracking.** Each marker lives from the commit that added it to the commit that removed it.
    - These continue the same marker: a line that moved inside its file, a line moved to another file in the same commit, a rewording in place (half its words kept), and a line removed and added again with the same text within 90 days (a two-step move, a revert).
    - Renamed files carry their markers.
  - **The window** is markers added from 2018-01-01 to 2024-12-31, by mainline commit time, so every one has at least 21 months of follow-up. The histories start in 2015 (VS Code), 2016 (Next.js) and 2020–2021 for the rest.
  - **Survival** is Kaplan–Meier, censored at each repo's pinned commit.
  - **Same author** compares the adding and removing commits' author name or email. First-parent merge commits carry the merger, not the code's author.
  - **Reconciliation:** the markers this tracker finds alive at the pinned commit match the parsed inventory in the same scope.
    - zod 1/1, hono 0/0, tRPC 15/15, Excalidraw 84/84, VS Code 40/40
    - Vite 28/25, Astro 42/39, Next.js 710/700
    - The differences are marker lines the line regex takes for comments and the parser doesn't (markers inside strings), and the reverse.
- **How they were removed** (`--classify`), after Zampetti et al.'s four scenarios (MSR 2018, §2.2.1: class removal, method removal, method not changed, method changed).
  - For each removal of a marker added in the window, both versions of the file are parsed with TypeScript.
  - The marker's innermost enclosing function is looked up after the commit by nested name: class, method, function, function-valued variable or property, or a callback by its callee. The outcome is one of:
    - **file deleted**
    - **function deleted:** no function with that name after the commit
    - **function unchanged:** identical apart from comments and whitespace
    - **function changed**
  - A top-level marker is judged on the statement after it: **unchanged**, **changed or removed**, or nothing follows.
- **Removal sample** (`--sample`): seeded (20261018), stratified by repo and automatic kind, up to 12 per repo (16 for Next.js), 89 removals in all. Its worksheet shows the commit message and file list, and the hunk that removed the marker (or, for a deleted file, 30 lines around it).

### 3.8 Hand classification (`todo-sample.cjs`)

- **Pinned sample:** seeded (20261018), one marker per comment, 102 items in all, each shown with 12 lines of code either side and its permalink. Shares are weighted by each repo's TODO-family comments.
  - By repo: zod 1 (all), tRPC 6, Vite 8, Astro 10, Excalidraw 14, Next.js 40, VS Code 10.
  - React set: Supabase 8, Radix 3, React Aria 2.
- **Codebook** (in `sample.json`; checked against the papers):
  - **type**, one per comment, the most meaningful, as Maldonado and Shihab (2015) did:
    - design: "a problem with the design of the code … workarounds or a temporary solution"
    - defect: code that "does not have the expected behavior"
    - requirement: "incompleteness of the method, class or program"
    - test and documentation
  - **on hold**, after Maipradit et al.: the comment "contains a condition to indicate that a developer is waiting for a certain event or an updated functionality having been implemented elsewhere". Raters also recorded what it waits on.
  - **valid** at the pinned commit; **resolvable in its own file**; **changes behaviour** if done; **deleting it loses information** a maintainer would want
- **Removal codebook** (in `removal-sample.json`): addressed, already done, dropped with the debt remaining, code deleted, code moved, rewritten for another reason, unclear; and whether the commit message mentions the task.
- **Raters.**
  - Rater 1, a Claude subagent with read-only access to the clones and the history clones, labelled all items.
  - Rater 2, a separate Claude subagent, labelled seeded blind subsets (36 pinned, 30 removals) without seeing rater 1's labels.
  - Both are Claude models, so agreement measures how consistently the codebook applies.

### 3.9 Agent runs (`todo-agent-runs.cjs`)

- **Scope:** every run under `research/agent-experiment/results/*/runs/` and `superseded-runs/`.
- **Inputs:** the net diff (`diff.patch`), each attempt's or step's own agent patch (`attempt*/agent.patch`, `step*/diff.patch`), and the subject before and after.
- **Marker lines** are TODO, FIXME, XXX or HACK in any case after a comment opener, or `@todo`.

### 3.10 Agent-experiment subjects (`todo-examples.cjs`, `todo-oracle.cjs`)

- **Choice.** Three TODOs flagged by Oxlint's `no-warning-comments`, from the survival data and the linked issues. They were chosen so the right response differs, and the project's own later action was found in its history.
- **Checks.**
  - Every block the headers call verbatim is compared with the file at its commit (`git show`).
  - Each subject is linted in every configuration and type-checked with `examples/todo-comments/tsconfig.json`.
- **The oracle** transpiles a file and runs it in a fresh Node process against stubs, which route every external call through the subject's exported `harness`. It compares the trace with the pristine subject's (§9).
- **Variants:** 20 hand-made edits, each linted, type-checked and run through the oracle: the right response, the project's own change, deletions, rewordings, moving the word, and "doing" the task.

## 5. Calibration and the evasion map

77 cases; the matrix is in `tables.md` §6.

- **What every linter reports:**
  - `// TODO: …` in any case (`//todo`, `Todo:`, `ToDo:`), `/* FIXME */` and `// XXX: …`
  - a block comment whose second line opens with TODO
  - `TODO(#12)`, `TODO(alice)`, a URL, `TODO-APP:`
  - trailing comments, JSX comment children and comments in JSX attributes
- **Never comments:** the word in a string, a template literal, JSX text or an identifier. `<div>// TODO …</div>` is JSX text: `react/jsx-no-comment-textnodes` and Biome's `noCommentText` report it, and the TODO rules don't.
- **What only `no-warning-comments` reports:**
  - `XXX`: sonarjs has no XXX rule
  - `Todo` opening the comment (T03, T35): sonarjs reads it as prose
  - a TODO followed by a Jira-style key (T15, T16, R25): sonarjs skips them
- **What only sonarjs reports:**
  - a TODO in the middle of a comment (T19), or on a later JSDoc line (T10)
  - a TODO after decoration: `// - TODO`, `// * TODO`, `// [TODO]`, `// **TODO**`, `/* ** TODO */`
  - `TODO_`, with a trailing underscore
  - a TODO in a `@ts-expect-error` reason (T30, R24) or an `oxlint-disable` reason (T33)
- **What nothing reports:**
  - the JSDoc `@todo` tag (T09), and a lower-case `todo` at the end of a comment (T20)
  - `eslint-disable` reasons, including one that disables `no-warning-comments` itself (T31, T32)
  - the plural `TODOs`, `todo_list` and `TODOx`
- **unicorn reports 8 of its 14 cases:**
  - two dates (U03)
  - a package version reached (U04)
  - a dependency installed (U06) or removed (U08)
  - a dependency version (U09) or the Node engine (U10) reached
  - malformed conditions: whitespace (U11) and a missing `@` (U12)

  With Ultracite's options it never reports an expired date (U01), nor a dependency that isn't installed (U07), a version not yet reached (U05), or a condition written in prose (U14).
- **Rewordings that silence every linter:**
  - NOTE:, Later:, TBD:, Pending:, Follow-up:, HACK:, BUG:, or a plain sentence (R01–R08)
  - `TO DO`, `TO-DO`, `T0D0`, a Cyrillic `ТОDО`, a zero-width space, or full-width letters (R15–R20)
  - `TODOx` (R22), or moving the text into a string (R23)
- **Rewordings that silence only `no-warning-comments`**, which is all of Oxlint's default presets: moving the word off the start (R09) and any decoration in front of it (R10–R14).

## 6. What the fix pass does first

- **None of the four rules has a fix or a suggestion.** `oxlint --fix` and `--fix-dangerously` change no comment in any case, with either config.
- **`eslint --fix`** reflows three single-line block comments (`/* FIXME */` → `/*\nFIXME\n*/`), through `unicorn/single-line-block-comment-style`. Afterwards the rules still report T06, and still miss T09 and R14.
- **`biome check --write --unsafe`** turns the JSX text `// TODO handle the empty case` into a `{/* TODO handle the empty case */}` comment (`noCommentText`'s unsafe fix), which `no-warning-comments` then reports.
- **So `ultracite fix` hands every TODO to the agent as written.**

## 7. Findings worth stating carefully

- **The rules see the word, not the debt.** They report a marker by its spelling and position.
  - They can't tell a stale TODO from a known bug, or from a reminder waiting on upstream.
  - The hand sample says 87% of the TODOs they flag carry information a maintainer would want.
  - A TODO that names an issue, an owner or a condition is reported exactly like a bare one.
- **Every silencing edit looks the same.** On the subjects, deleting the marker, rewording it to NOTE and moving the word off the start all clear `no-warning-comments`. Whether that was right depends on the TODO (§9). Only "Left for review" keeps a valid TODO and gives an honest result.
- **Rewording is what the help asks for.** Oxlint's "Remove or rephrase this comment" names the evasion, and Ultracite's prompt doesn't warn against it for this rule.
- **TODOs are short-lived on the mainline, but not because they're done.** 78% of those added from 2018 to 2024 were gone by October 2026, half within six months. Yet in the hand sample only 55–58% of removals did the task. The rest went with deleted or rewritten code, or the comment was dropped.
- **Coverage differs by linter.** Oxlint's default presets see 90% of TODO-family markers, ESLint and Oxlint with js-plugins see nearly all, and Biome sees none. unicorn's rule, the one designed to make TODOs expire, can't expire a date as Ultracite configures it.
- **Next.js is a different kind of project for TODOs.** It has 77% of the corpus's markers, tags them by topic and feature, and keeps them longer than the smaller repos.

## 8. Caveats

- **Snapshot and mix.**
  - The repos are at their 2026-10 HEADs.
  - The survival window ends in 2024, so every marker in it has at least 21 months of follow-up. But markers added in 2018–2019 exist only for VS Code and Next.js.
  - Seven of the eight corpus repos are libraries or frameworks, and none of them enables these rules. A codebase that does lint TODOs won't look like this.
  - Next.js is 40% of the lines and 77% of the markers; pooled numbers are given without it too.
- **What counts as a marker is a definition.** Prose and placeholders were excluded by rules that were spot-checked by hand, not one by one. The rule terms (TODO, FIXME, XXX) are unaffected: every one in a marker position is counted, and the linters' diagnostics land on them exactly.
- **The format fields are heuristics.**
  - "Strict condition" is a regular expression for event-shaped phrases, and the loose word list over-counts.
  - Owners are people only when they match a commit author. Supabase has no history clone, so its `TODO(name)`s count as topics.
- **History is the mainline only, and line-based.**
  - Markers inside strings that look like comments can be counted, and markers in comments without an opener on the line can be missed. The reconciliation finds 3 more in Vite and Astro and 10 more in Next.js than the parsed inventory.
  - A marker reworded beyond half its words, or moved and changed in the same commit, ends there and a new one begins.
  - Function matching is by nested name, so a renamed function counts as deleted.
  - VS Code's history covers `src/vs/editor/common` only, and Next.js's covers its `packages/next` source directories. Zod and Vite start in 2020, Astro and hono in 2021.
- **The classifications are judgment.**
  - Claude raters with codebooks labelled both samples, and the second rater saw only a subset.
  - "Valid" agrees least (κ 0.54).
  - The stale-issue verdicts and the decision history have one rater: me.
- **The issue states are as of 2026-10-18,** read with `gh`. One PR closed after the pinned commit is counted as open at it.
- **The agent runs are from other topics.** Their subjects contained no TODO, so they can't show how an agent treats one. That's what the subjects in §9 are for.

## 10. Notes on Ultracite itself

These are raised for Hayden, not fixed.

1. **`unicorn/expiring-todo-comments` can't expire a date as Ultracite configures it.**
   - Ultracite sets no options.
   - Since eslint-plugin-unicorn 65.0.0, `checkDates` defaults to `false`. v64 had `ignoreDates: false`, which did check dates.
   - Ultracite crossed that version in 0b8fc122 ("Upgrade ESLint and its plugins", unicorn ^64 → ^70).
   - The v65.0.0 release notes say the opposite ("Make `checkDates` option `true` by default (#3044)"); the code and the v77 docs say `false`.
   - With `allowWarningComments: true` it also never reports a TODO without a condition, so on the corpus it reports nothing.
   - Setting `checkDates: true` would make dated TODOs expire.
2. **The help text and the prompt point at the evasion.**
   - Oxlint's `no-warning-comments` help is "Remove or rephrase this comment", and its docs' correct example is a `// Note:` comment.
   - Ultracite's prompt tells agents that restyling won't clear a diagnostic; for this rule it does (§5).
   - The AGENTS.md template (`packages/cli/src/data/rules.ts`) and the skill's code standards say nothing about TODO comments.
3. **Coverage differs by linter more than the rule names suggest.**
   - Oxlint's default presets have `no-warning-comments` only, which sees 90% of TODO-family markers. JSDoc TODOs and `@todo` tags aren't seen.
   - js-plugins and ESLint add the sonarjs rules, which see nearly all of them, but skip TODOs followed by a tracker key (Next.js's `TODO(NAR-…)`).
   - Biome has no rule at all, so a Biome project gets no TODO checking.
   - With js-plugins or ESLint, a TODO is usually reported twice (`no-warning-comments` and `todo-tag`).
4. **`no-warning-comments` can't be configured to see JSDoc TODOs on later lines.**
   - `decoration: ["*"]` plus an `@todo` term catches `/** @todo */` and `/* ** TODO */` (checked in ESLint).
   - A TODO on a later JSDoc line needs `location: "anywhere"`, which also reports prose.
   - The sonarjs rules are the only ones that read every line.
5. **No rationale was recorded** for any of these rules.
   - `no-warning-comments` came in with the first ESLint config (e403fb15, 2022) and was dropped with the move to Biome (#140, 2024).
   - It returned with every-rule policies: ESLint's `all` (V7, #466) and Oxlint's explicit list (#660).
   - The sonarjs rules came with the JS-plugin bridge (44403937) and moved to js-plugins for speed (#742).
   - No issue or PR discusses them.
6. **The rules have no fix**, so `ultracite fix` hands every TODO to an agent, one per marker, with no guidance on which ones to keep.
