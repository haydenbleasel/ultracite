# Sorting object keys in real TypeScript codebases: measurement report

The data behind the post on sorting object keys, measured on 2026-10-19 and 2026-10-20. Generated tables are in `tables.md`. The machine-readable results are:

- `inventory.json`: the rules per linter and preset, with options, defaults, messages and fix kinds
- `census.json`: every object literal in the corpus, aggregated per repo and pooled (rows in `out/sort-keys/census/`)
- `rule-census.json` and `rule-census.md`: the shared Oxlint census (core + react)
- `corpus-lint.json`: the three rules on all thirteen repos, raw and reported, joined to objects, with every disagreement explained, and the messages
- `calibration.json`: the calibration matrix, what every fix pass does to each case, and the behaviour and type results
- `fixes.json`: what Oxlint's and Biome's fixes do to the corpus, the static signs of a behaviour change, and the type-check overlay (rows in `out/sort-keys/fixes/`)
- `iteration-check.json`, `effect-order-check.json`, `inference-check.json`: the hand checks of the rewrites
- `markers.json`: each repo's lint and format configs, sorting plugins, disable comments and sorted share
- `history.json`: where keys get added on each project's mainline, and the merge simulation (rows in `out/sort-keys/history/`)
- `sample.json` and `classifications.json`: the hand classification, both raters
- `agent-runs.json`: key order in the agent experiment's own committed runs
- `decision-history.json`: how Ultracite came to sort keys

The agent-experiment subjects are in `corpus/examples/sort-keys/`. Everything is regenerated by `research/corpus/scripts/sort-keys-*.cjs` (§9).

Terms used throughout:

- **Object:** an object literal with two or more members, spreads included. That's what all three rules look at: their `minKeys` is 2 and counts spreads. Object patterns, type literals, interfaces, enums and JSX attributes aren't objects here.
- **Sorted:** no adjacent pair of named keys out of order inside a group, under a rule's own reading.
  - ESLint and Oxlint compare strings by code unit: `$`, digits, capitals, `_`, then lower case.
  - Biome uses natural order: `A a B b`, `9 < 10`, and `_` and `-` before digits.
  - ESLint and Oxlint start a new group at a spread. Biome also starts one at a computed key that isn't a literal.
- **Rewritten:** an object whose key order a fix changed.
- **Raw and reported:** raw counts every occurrence, with disable comments neutralised. Reported honours the files' own disable comments, as `ultracite check` does.

## TL;DR

- **Corpus.** The same eight codebases, SHAs and 3,333 files (694,309 lines) as the earlier reports: 13,574 objects, 195.5 per 10,000 lines.
  - Ultracite's own CLI (432 objects), which enforces the rule, is listed separately.
  - The four React codebases from the accessibility post are a separate set (14,014 objects, 87% of them in Supabase Studio).

- **What Ultracite turns on.**
  - **Oxlint core:** `sort-keys`, `"error"`, no options (ascending, case-sensitive, not natural, `minKeys` 2). Its fix is a `conditional_fix`, which `oxlint --fix`, and so `ultracite fix`, applies.
  - **ESLint core:** `sort-keys` from `@eslint/js` `configs.all`, with the same defaults. It has no fix and no suggestions, and ESLint has frozen it.
  - **Biome core:** the `useSortedKeys` assist (natural order), which `biome check --write` applies. Off for `package.json`.
  - **TanStack presets:** all three are off, because sorting broke TypeScript inference (#762, #801).

- **Authors don't sort keys, but they do order them.**
  - **About as sorted as chance.** 34.9% of objects are already sorted, against 33.7% if every order were equally likely. For two keys it's 50.7% against 50%. The mean share of key pairs out of order is 0.48–0.52 at every size, as for a random order.
  - **The defining key goes first:**

    | Key | First | First if sorted |
    | --- | ---: | ---: |
    | `type` (1,221 objects) | 79.5% | 3.4% |
    | `name` | 88.7% | 14.4% |
    | `id` | 84.4% | 23.6% |
    | `kind` | 75.5% | 27.5% |

  - **Only the enforcing repo is sorted.** Ultracite's CLI is 100% sorted. The others range from 18.3% (VS Code) to 43.9% (Excalidraw).

- **What the linters report.**

  | Linter | Diagnostics | Objects |
  | --- | ---: | ---: |
  | ESLint | 16,861 (one per key out of place) | 8,839 (65.1%) |
  | Oxlint | one per object | 8,822 (8,195 with a fix) |
  | Biome | one per object | 8,816 |

  - **Three reimplementations predict every report exactly**, object by object, on all thirteen repos.
  - **The linters disagree on 17 to 39 objects.**
    - ESLint names a computed `[key]` and Oxlint skips it: 17.
    - Biome splits groups at computed keys: 17.
    - Biome's comparator (`A a B b`, `9 < 10`, `_` first) differs from Oxlint's on 22.
  - **Disable comments don't matter here.** No repo has one naming these rules. Raw and reported differ only by 6 Excalidraw objects under a file-wide `/* eslint-disable */`.

- **What the fixes do.**
  - **Oxlint rewrote 7,391 of 8,822 objects (84%) in one pass**, in 1,464 files, +22,213 −22,307 lines.
    - **No fix for 562:** a comment between keys (357), a comment before the first key or after the last (130), spreads splitting the keys into groups (64), a computed key (11).
    - **869 had a fix that wasn't applied in that pass.** 798 of them lie inside another object the same pass rewrote, and 6 are under the disable comment.
    - **1,425 objects are still reported after one `ultracite fix`** and go to an agent. Most of them get a help text that spells out the sorted order.
  - **Biome rewrote all 8,816**, in 1,516 files, ±28,994 lines. It moves every comment with the key below it, so 831 of 881 heading comments end up above different keys.
  - **Neither fix moves a key across a spread, and every fixed corpus file parses.** But both have edge cases:
    - **A swallowed brace.** A key with a trailing `//` comment can move last when the object closes on the same line. The comment then swallows the `}` and the file doesn't parse, in both Oxlint and Biome (calibration K50). Formatted code never has that shape, so the corpus has none.
    - **A comma inside a comment.** Oxlint moves the object's trailing comma into such a comment. That happened to 10 comments in the corpus.
    - **An unstable sort.** In objects over 20 keys, Oxlint can swap keys with the same name. That changed which duplicate key wins in 88 of 300 generated objects, and swapped a getter/setter pair in Vite's dev server object. The corpus has no duplicate keys.

- **How often sorting changes behaviour: rarely, and invisibly when it does.**
  - **Type checks.** Every repo was type-checked with its own tsconfig before and after both fixes, and no fix added a TypeScript diagnostic. That holds for the 15 objects in zod and hono (whose types fully resolve) where two context-sensitive callbacks swap. Unresolved imports elsewhere hide inference.
  - **Where the rewrites go.** Of Oxlint's 7,391 rewrites:
    - **276 reach something that observes order:** JSON.stringify (78), a spread (79), Object.keys/values/entries (45), Object.assign (28), logs (27), serialisers (23).
    - **6,607 escape where the analysis can't follow:** exported, returned, or passed to a function.
  - **Iterated objects, read by hand.** All 46 rewrites seen iterated were read: 24 harmless, 5 change only bytes or header order, 14 change a list a user sees. **3 change behaviour:**
    - Hono's encoding preference: a client that accepts gzip and zstd gets gzip.
    - Excalidraw's colour-picker Tab order.
    - The default choice of Next.js's upgrade prompt.

    None is caught by the project's tests.
  - **Side effects.** A sample of 16 of the 522 rewrites that swap side-effecting values was read; none of the swaps matters.
  - **Hand sample of 100 flagged objects** (blind second rater on 36):
    - sorting changes behaviour in none
    - the order is observable in 16% (κ 0.87)
    - sorting loses information a reader uses in 32% (κ 0.85)
    - sorting is an improvement in 0.3%

- **Merge conflicts.**
  - **Where keys go.** On the mainlines, 8,586 commit-object events added 9,964 keys to 3,884 objects: 47.5% at the end, 44.5% in the middle, 7.5% at the start.
  - **Replayed concurrently.** Two consecutive additions to the same object were replayed as concurrent edits with `git merge-file`, 4,441 pairs:

    | Layout | Conflicts |
    | --- | ---: |
    | authors' positions | 37.4% |
    | sorted positions | 24.9% |
    | both appended at the end | 100% |

    Counted once per pair of commits, it's 38.5% against 27.3%.
  - **Without a rule, sorted objects don't stay sorted.** Only 46% of keys added to an already sorted object went where sorting would put them.

- **Agents in our earlier experiments wrote sorted keys.** Across 188 committed runs, Claude Code and Codex wrote 45 new object literals, and all were sorted. All of them are inline style objects in the accessibility runs, whose subjects the fix pass had already sorted. No agent reordered an existing object.

- **Agent-experiment subjects** (§10). Each is flagged by ESLint's `sort-keys` and checked by a behaviour oracle:
  - **A, Vite's `send()`:** a lookup map and an options bag; sorting changes nothing.
  - **B, Astro's JSON logger:** log lines change byte order. JSON parsers don't care, but Astro's own tests compare the strings.
  - **C, Hono's `serveStatic`:** the key order is the compression preference. Sorting serves gzip instead of zstd, and Hono's tests still pass.

  Oxlint's fix, which runs before any agent, sorts all three.

## 3. Method

### 3.1 The object census (`sort-keys-census.cjs`)

- **Parser.** Each file goes through ESLint's own `Linter` with `@typescript-eslint/parser` and a local rule that reports nothing. That gives the AST and scope analysis ESLint's `sort-keys` sees. All 3,333 corpus files parse.
- **Per object:**
  - **Each member's name as each linter reads it:**
    - ESLint: `getStaticPropertyName`, or the identifier of a computed `[foo]`
    - Oxlint: `PropertyKey::static_name`
    - Biome: `AnyJsObjectMember::name`, the raw token text
  - **Its key kind:** identifier, quoted, numeric, computed literal, computed identifier, computed expression, or spread.
  - **Its value kind**, and whether the value runs code (calls, `new`, assignments, `++`, `await`, `yield`, tagged templates, `import()`, outside nested functions) or reads state.
  - **Comments and blank-line gaps** between members.
- **Order:**
  - whether the object is sorted under each rule's grouping and comparator
  - ESLint's report count
  - Oxlint's fix blocker, from `collect_fixable_properties`
  - the chance a random order would be sorted: the product over groups of the ties' factorials over the group size's factorial
  - the share of key pairs out of order: a Kendall distance, 0 for sorted and 0.5 for random
- **Flow.** Where the object goes, followed through:
  - `as`, `satisfies`, `!`, `?:`, `&&` and `await`
  - variables, through every reference in their scope, two aliases deep
  - the outermost literal, for nested objects and arrays
- **Sinks.** Along the way, every order-observing sink is recorded:
  - JSON.stringify, and what its string goes into
  - Object.keys / values / entries / getOwnPropertyNames and Reflect.ownKeys, and whether the loop over them stops at the first match
  - for-in, Object.assign, a spread, a rest pattern
  - URLSearchParams, Headers and FormData
  - serialisers by name, and loggers
- **Escapes and local uses.** Escapes are exports, returns, arguments, JSX props and member assignments. Local uses are member reads and writes, `in` and destructuring.
- **Order-sensitive shapes:**
  - two context-sensitive callbacks (functions with an unannotated parameter) in a call argument
  - package `exports`-style condition keys: at least one of `import`, `require`, `default`, `module-sync`, `node-addons`
  - a CSS shorthand and one of the longhands it resets, from explicit tables (`border` doesn't reset `borderRadius`; `flex` doesn't reset `flexDirection`)
  - `.sort()` specs, JSON-schema `properties` and zod-style `object({…})` shapes
- **Also counted:** object patterns, type literals and interfaces, enums and JSX attribute lists, which sort-keys doesn't read.

### 3.2 The rules (`sort-keys-inventory.cjs`) and their reimplementation (`sort-keys-lib.cjs`)

- **Sources read,** fetched read-only with `gh api`:
  - ESLint 10.12.0 `lib/rules/sort-keys.js`, as installed.
  - Oxlint's `crates/oxc_linter/src/rules/eslint/sort_keys.rs` and `oxc_ast`'s `PropertyKey::static_name`, at `oxlint_v1.86.0`.
  - Biome's `use_sorted_keys.rs`, `biome_analyze/src/utils.rs`, `biome_string_case` and `AnyJsObjectMember::name`, at `@biomejs/biome@2.5.15`.
- **What's reimplemented:** names, grouping, comparators, the report count, Oxlint's fix conditions, and the order each fix produces. Biome's natural order is a port of `Collator::cmp` over UTF-8 bytes with the CLDR weights table.
- **Checks:**
  - **Self-test.** Before the corpus run, 400 generated objects with keys drawn from `aAbBzZ_$09-1x` went through both fixes, and the predicted orders matched exactly.
  - **Corpus.** `sort-keys-linters.cjs --corpus` checks every object against the real linters, and any difference fails the run.
- **Options a file gets:**
  - Oxlint: from `configuration_schema.json` and `--print-config`.
  - ESLint: `calculateConfigForFile` for `.ts`, `.tsx`, `.js` and `.test.ts`, for core, core + react, core + tanstack and core + type-aware.

### 3.3 The linters on the corpus (`sort-keys-linters.cjs --corpus`)

- **Repos and modes.** All thirteen repos, raw and reported.
  - Oxlint and Biome lint a mirror with every `eslint-`/`oxlint-disable` and `biome-ignore` rewritten to the same length.
  - ESLint lints the clones in place, read-only.
- **Joining diagnostics to objects:**
  - ESLint reports a key, so it's matched by the key's offset.
  - Oxlint reports the object, matched by the line and column of `{`.
  - Biome reports the member list, matched by its first member's start.
- **Disagreements.** Each object one linter flags and another doesn't is attributed:
  - **to names:** a computed `[identifier]`
  - **to grouping:** one linter's verdict re-evaluated with the other's grouping
  - **to the comparator:** the first character where the two comparators disagree on an adjacent pair
- **Message examples** are the first by repo, file and line, so they don't depend on Oxlint's parallel output order.

### 3.4 Calibration (`calibration/sort-keys/`, `sort-keys-calibration.cjs`)

- **80 cases:**
  - **55 shapes (K01–K52).** Case and natural numbers; `_` and `$`; numeric and quoted keys; every kind of computed key; spreads at the start, middle and end; comments of every placement; blank-line groups; methods, getters and setters; shorthand; `__proto__`; duplicates; nested objects; `as const`; `satisfies`; style objects. Type literals, interfaces, enums, destructuring and JSX attributes are included as negatives. Two comment edge cases are in a file of their own.
  - **20 runnable behaviour cases (B01–B20)** in `behaviour.ts` and `behaviour.js`.
  - **5 inference cases (I01–I05)** in `inference.ts`: TanStack Query-style mutation options, TanStack Router-style route options, a store, and two controls.
- **Configurations:** Oxlint (init's config, and `sort-keys` alone), ESLint core + react, and Biome (core, and the action alone).
- **Fix passes:**
  - `oxlint --fix`, alone and with init's config
  - `biome check --write`, alone and with core
  - `eslint --fix`
  - a hand sort by ESLint's own grouping, which is what clearing ESLint's rule takes, since it has no fix
- **Recorded:** each object's key order after each fix, each comment's anchor, and what's still reported.
- **How each kind of case is checked:**
  - **Behaviour cases** are transpiled with TypeScript and run in a fresh Node process before and after each fix, and their results compared with key order kept.
  - **Inference cases** are type-checked.
  - **Style cases** are rendered with `renderToStaticMarkup`, and the style attribute is resolved with Lightning CSS's `transformStyleAttribute`, which collapses shorthands and longhands as the cascade does.
- **An unstable-sort probe.** 300 seeded objects of 21 to 50 keys plus one duplicated key, fixed by Oxlint alone, then imported to see which value of the duplicate survives.

### 3.5 The fixes on the corpus (`sort-keys-fixes.cjs`)

- **The run.** Copies of every corpus file get one `oxlint --fix` with `sort-keys` alone, or one `biome check --write` with the action alone, as one `ultracite fix` would. A second pass is run only to see what's left, then undone.
- **Matching.** Objects before and after are matched by their path from the root, naming properties by their key's text and spreads by position.
- **For each rewritten object:**
  - the new order against the prediction
  - where each comment sits before and after
  - commas that moved into a comment
  - heading comments that no longer head the same keys: an own-line comment that isn't JSDoc, above two or more keys, up to a blank line or another comment
  - blank-line gaps
  - keys moved across a spread
  - the §3.1 signs, for the key pairs the fix swapped
- **Parse check.** Every fixed file is parsed again.
- **Type-check overlay.** One TypeScript program per repo, from its own tsconfig, with the fixed files swapped in through the compiler host.
  - **Tsconfigs:** the root's, except `packages/astro`, `packages/next`, `packages/vite/tsconfig.base.json` and VS Code's `src/tsconfig.base.json`.
  - **Matching diagnostics.** Diagnostics are compared by file and code. TypeScript prints properties in declaration order, and its excess-property check names the first unknown property in source order. With rollup's types unresolved, 12 Vite plugin objects name a different hook after sorting; nothing else changed.

### 3.6 Hand checks of the rewrites (`sort-keys-hand-checks.cjs`; one rater)

- **Iteration:** all 46 Oxlint rewrites whose order the analysis saw reach Object.keys/values/entries or for-in, read with their uses at the pinned commit. Each is labelled semantics, display, observable or harmless.
- **Evaluation order:** a seeded sample (seed 1019) of 16 of the 522 rewrites where two side-effecting values swap.
- **Inference:** the objects where two context-sensitive callbacks swap, set against the type-check overlay.
- **Overlaps:** which of Oxlint's fixable-but-unrewritten objects lie inside another rewritten object.
- **A guard:** the script fails if a population changes and a verdict is missing.

### 3.7 Policy (`sort-keys-markers.cjs`)

- **Which configs:** every ESLint (flat and legacy), Biome, Oxlint, Prettier and dprint config at each pinned commit.
  - **Source:** `git ls-tree` and `git show` on the history clones, or the corpus clone for the React set and Ultracite.
  - **Left out:** configs for tests, fixtures, examples and templates, and Ultracite's presets.
- **What's recorded:**
  - lines naming `sort-keys`, `sort-keys-fix`, perfectionist, `sort-objects`, `typescript-sort-keys` or `useSortedKeys`
  - shared configs that would enable `sort-keys` (`eslint:all`, `configs.all`)
  - sorting plugins in `package.json` files
  - disable comments naming these rules

### 3.8 History and the merge simulation (`sort-keys-history.cjs`)

- **Clones.** The TODO post's bare history clones.
  - Every pinned SHA is in its clone.
  - Only `git log` and `git cat-file` ran on them, with `GIT_NO_LAZY_FETCH=1`. No blob was missing.
- **Scope.** Every first-parent commit modifying a file in the measured package's source, in every layout it has had (`todo-history.cjs`'s scopes): 28,886 commits and 87,669 file versions, parsed with TypeScript.
- **Matching objects.** Each object is identified by an anchor: the chain of variable, function, property, call-argument, JSX-attribute, return and assignment names above it. Only anchors unique in both versions of a file are kept, and renames keep the lineage.
- **A gain event.** The keys after are the keys before plus new ones, with the old keys in the same order and none removed, and the object had at least two keys before.
  - **Position.** Each new key is classed as start, middle or end relative to the old keys of its own spread group, or as a new group.
  - **Sortedness.** Whether the object was sorted before and after (ESLint's reading), and whether the new key went where sorting would put it.
  - Commits that only reordered keys are counted too.
- **Merge simulation.** For every object with two consecutive gain events in different commits:
  - **Base:** the object before the first event.
  - **The two edits:** each event's new keys inserted into that base, in three layouts:
    - at the author's position: after the nearest old key that precedes it
    - at sorted positions, with the base itself sorted
    - both appended
  - **Rendering:** each property is a block of its real source lines, one property per line, with trailing commas, and again without.
  - **Merging:** `git merge-file -p` on scratch files, whose exit status is the conflict count.
  - **Counting:** by pairs, and by pairs of commits, because one commit often adds the same key to many objects.

### 3.9 Hand classification (`sort-keys-sample.cjs`)

- **The sample.** 100 objects ESLint reports, seeded (20261019) and frozen in `sample.json`.
  - **By repo:** zod 10, hono 8, tRPC 8, Vite 12, Astro 12, Excalidraw 14, Next.js 20, VS Code 10, plus Supabase 6 (listed, not in the shares).
  - **By flow:** a quarter of each repo's draw comes from objects whose order the analysis saw observed. The rest is split between escaping and local objects in proportion.
- **Weighting.** Shares are weighted to the flagged population by repo and stratum.
- **The worksheet.** Each item shows the object's code, its keys as written and as sorted, its flow labels, its references and a permalink.
- **Codebook:**
  - **reason:** arbitrary; grouping; mirrors (a type, a parameter list, a protocol, another object); data-flow; display; priority; importance (the defining key first); unclear
  - **behaviour if sorted:** no; observable (visible, but nothing should depend on it); yes (semantics); unclear
  - **information loss if sorted**
  - **improvement if sorted:** yes, neutral, no
- **Raters.**
  - Rater 1, a Claude subagent with read-only access to the clones, labelled all 100.
  - Rater 2, a separate Claude subagent, labelled a seeded blind subset of 36.
  - Both are Claude models, so agreement measures how consistently the codebook applies.

### 3.10 Agent runs (`sort-keys-agent-runs.cjs`)

- **Which runs:** every run under `research/agent-experiment/results/*/runs/` and `superseded-runs/`, 188 in all (93 Claude Code, 95 Codex).
- **What's compared:**
  - the subject before against the final file
  - each attempt's input against the agent's edit
  - the agent's edit against what Ultracite's fix pass left
- **What's counted:**
  - sort-keys reports
  - object literals at a new path, written or moved (an object with the same keys existed before)
  - objects reordered: the same path and keys in another order

### 3.11 Subjects (`sort-keys-examples.cjs`, `sort-keys-oracle.cjs`)

- **Choice.** Three objects ESLint flags, in code that type-checks once its imports are stubbed. They were chosen so the right response differs, and their history was read on the history clones.

- **The oracle** transpiles a file and runs it in a fresh Node process against fakes. Its traces keep key order and exact strings.
- **Variants.** 14 hand-made edits, each linted, type-checked and run.

## 5. Calibration

80 cases; the matrix is in `tables.md` §4.

- **Comparators:**
  - `a, B, c` is unsorted for ESLint and Oxlint (`B < a`) and sorted for Biome (K01).
  - `a10, a2, a1` sorts to `a1, a10, a2` in Oxlint and `a1, a2, a10` in Biome (K02).
  - `b, _a, $c, a` sorts to `$c, _a, a, b` in Oxlint and `_a, $c, a, b` in Biome (K03).
  - Numeric keys `1, 10, 2` are sorted for ESLint and Oxlint and not for Biome (K04).
  - `0x10, 2, 1e3` sorts to `1e3, 0x10, 2` in ESLint and Oxlint, which read 16 and 1000, and to `0x10, 1e3, 2` in Biome (K44).
- **Computed keys and spreads:**
  - `b, [key], a`: ESLint reports `'a' should be before 'key'`, Oxlint reports without a fix, and Biome reports nothing (K07).
  - A spread in the middle: Oxlint reports without a fix, and Biome sorts each side (K10). A spread at either end: both fix (K11, K12).
- **Comments:**
  - **Line comments above keys:** Oxlint doesn't fix; Biome moves them with their keys (K13).
  - **JSDoc above keys and `// …` after commas:** both move them with their keys (K14, K15).
  - **Section headings:** Oxlint doesn't fix; Biome separates them from their groups (K16).
  - **A swallowed brace.** A trailing `//` comment on a key that moves last, with `}` on the same line, swallows the brace in both, and the file no longer parses (K50).
    - Oxlint: `{ a: 2,\n  b: 1, // trailing on b };`
    - Biome: `{ \n  a: 2, b: 1, // trailing on b};`
  - **A comma into the comment.** Oxlint moves the object's trailing comma into such a comment (K51).
- **Blank lines:** Oxlint flattens them (K17), and Biome keeps one with the key below it.
- **Duplicates:**
  - Both fixes keep `b, a, b` in source order in small objects (K22).
  - **Oxlint's unstable sort swaps duplicates in larger objects.** In a 23-key object, the winning value changes from `"second"` to `"first"` (K52, B06c). Of 300 seeded objects with 21–50 keys and one duplicate, 88 swapped. Biome's sort is stable.
- **Not object literals:** sort-keys ignores type literals, interfaces, destructuring, enums and JSX attributes. Biome core sorts interfaces (K25) and JSX attributes (K29).
- **Behaviour, run in Node** (`tables.md` §4.1). Oxlint's fix changes 19 of the 23 runnable results and Biome's 18. For most of them that means only iteration order or bytes. The clearest:
  - **Evaluation order:** side effects in values run in another order (B01, B04), and so do two `await`ed values (B14). `{ b: i++, a: i++ }` gives `a: 0, b: 1` instead of `a: 1, b: 0` (B03).
  - **First match:** a for-in over route prefixes returns `home` for every URL instead of `create, list, home` (B09), and an exports-style condition map resolves `./index.js` for every condition (B10).
  - **Bytes:** `JSON.stringify`, `Object.keys`, `URLSearchParams` and a sha256 of JSON all change (B07, B08, B16, B20).
  - **CSS:** `{ marginTop: 4, margin: 0 }` renders `margin-top:4px;margin:0` (effective `margin:0`) before the fix and `margin:0;margin-top:4px` (effective `margin:4px 0 0`) after (K30b). The same holds for `borderColor` before `border` (K30c).
- **Unchanged by sorting:**
  - **An overriding spread** (B05): a key the spread already set keeps the spread's position.
  - **`__proto__`** still sets the prototype (B13).
  - **Integer-like keys** enumerate first, in numeric order, wherever they're written. B12's change is its two string keys.
  - **A getter** that reads keys declared after it still works (B18).
- **ESLint's grouping by hand.** A hand sort by ESLint's grouping also reorders `{ [kb]: …, [ka]: … }` (B02), which neither fix touches, because ESLint names computed identifiers.
- **Inference** (`tsc` on `inference.ts`). The original type-checks; after either fix or the hand sort, three cases break:

  | Case | What moves | Errors |
  | --- | --- | --- |
  | I01, TanStack Query-style | `onError` above `onMutate` | 2 × TS2339 `Property 'previous' does not exist on type '{}'` |
  | I02, Router-style | `component` and `head` above `loader` | 2 × TS18046 `'data' is of type 'unknown'` |
  | I03, a store | `render` above `state` | 1 × TS18046 |

  - **The controls hold.** A loader with no parameters isn't context-sensitive, so it's inferred first wherever it sits (I04). Annotating the later callback removes the dependency (I05).
  - **So only callbacks with unannotated parameters are inferred in source order.**

## 6. Findings worth stating carefully

- **The rule changes order, and order is rarely meaningless.**
  - **Behaviour changes are rare.** 3 of 7,391 rewrites, found by reading the 46 the analysis could follow, and none in a random 100.
  - **Information loss isn't.** A third of flagged objects carry an order a reader uses, and the defining key is first in three quarters of the objects that have one.
- **When sorting changes behaviour, nothing catches it.**
  - **No test or type notices.** Hono's tests pass with gzip preferred over zstd. Nothing checks the colour picker's Tab order or Next.js's default menu choice.
  - **The fixes are silent.** They're labelled safe, run in `ultracite fix` before any agent, and print nothing about what they reordered.
- **Inference breaks show only where types resolve.** The TanStack cases broke loudly (TS2339) in projects with their dependencies installed. Here no fix added a diagnostic, and only two repos could have shown one.
- **The fixes differ more than the rules.**
  - **Oxlint** refuses objects with comments, so it rewrites fewer and keeps comments with their keys. But it leaves 16% for an agent, needs a second pass for nested objects, and has two comment bugs and an unstable sort.
  - **Biome** always fixes, and reattaches heading comments to single keys.
- **Merge conflicts are the one claimed benefit with measured support here, and the measure is a simulation.** Sorted positions conflicted in 25% of replayed pairs, against 37% at authors' positions and 100% when both append.
- **Scanning isn't tested.** Nothing here measures how fast people find a key.

## 7. Caveats

- **Snapshot and mix.** The repos are at their 2026-10 HEADs. Seven of the eight corpus repos are libraries or frameworks, none enforces key sorting, and Supabase Studio is the only application.
- **The static flow analysis is shallow.**
  - **Scope.** It follows one scope, two aliases deep, plus nested literals and a few pass-through calls. It doesn't cross files or enter the functions an object is passed to, and 89% of rewrites escape it.
  - **First match.** Detection covers only a loop directly over `Object.keys` or `entries`. It missed Hono's encoding loop, which goes through a variable; reading every iterated object found it.
  - **By name.** Serialisers and loggers are matched by name.
- **Rater limits.**
  - **One rater** made the hand checks of the rewrites and the decision history.
  - **The classification** had two Claude raters, with the second blind on 36 items. Improvement agrees least (κ 0.44).
- **The type-check overlay is a lower bound outside zod and hono.** It matches by file and code, so a removed error and an added one of the same code in the same file would cancel.
- **History is the mainline only.**
  - Pull-request internals and concurrency are invisible.
  - Objects are matched by an anchor of names, so a rename or move in the same commit starts a new lineage.
  - Events that also removed or reordered keys aren't gain events.
- **The merge simulation is a model.**
  - It renders each property as its own block with uniform indentation. Real objects have one-line forms, comments and formatters that reflow, and real merges have more context.
  - It measures whether two insertions touch the same place, not how often teams hit conflicts.
- **The unstable sort depends on the Rust build.** It was measured on Oxlint 1.86.0, and `sort_unstable_by`'s tie order can change with the Rust version Oxlint is built with.
- **The agent runs are from other topics.**

## 8. Notes on Ultracite itself

These are raised for Hayden, not fixed.

1. **The fixes Ultracite runs first can change behaviour, while its prompt says to preserve it.**
   - Oxlint's `sort-keys` fix (`conditional_fix`) and Biome's `useSortedKeys` (safe) run in `ultracite fix` before any agent, and say nothing about what moved.
   - In the corpus they change Hono's encoding preference, Excalidraw's Tab order and Next.js's default menu choice. In the subjects they change Astro's log output, which Astro's own tests pin.
   - The TanStack exceptions (#762, #801) were the inference version of this.
2. **Biome's preset comment says `useSortedKeys` "Matches sort-keys in the oxlint/ESLint configs". It doesn't quite.**
   - Biome sorts naturally (`A a B b`, `9 < 10`, `_` first) and starts a new group at a computed key.
   - 22 corpus objects are sorted for one linter and not the other, as are 2 in Ultracite's own CLI (`hook-input.ts`).
   - Switching linters with `ultracite init` re-sorts those.
3. **Two comments in Biome core describe the wrong action.**
   - `useSortedProperties` is commented "Enforce ordering of a JavaScript object properties", but `biome explain` says it orders CSS properties.
   - `useSortedTypeFields` is commented "Enforce ordering of TypeScript type alias members", but it sorts GraphQL type fields.
4. **Biome core sorts more than the other presets.** It turns on `useSortedInterfaceMembers` and `useSortedAttributes`. ESLint's react preset turns `react/jsx-sort-props` off, and neither Oxlint nor ESLint sorts interface members.
5. **Upstream bugs to report.**
   - **Oxlint 1.86.0:**
     - A key with a trailing `//` comment that moves last swallows a `}` on the same line, leaving a file that doesn't parse.
     - The object's trailing comma moves into that comment.
     - `sort_unstable_by` swaps keys that compare equal, which changes which duplicate wins in objects over 20 keys.
   - **Biome 2.5.15** has the first bug too (calibration K50, K51, K52).
6. **Oxlint's fix pass needs two runs for nested objects.** One `ultracite fix` leaves 869 corpus objects reported, so an agent is handed them with a help that only spells out the sort.
7. **ESLint's handoff has one issue per key,** 1.9 per flagged object on the corpus.
8. **The AGENTS.md template and the skill's code standards say nothing about key order** (`packages/cli/src/data/rules.ts`, `skills/ultracite/references/code-standards.md`), including when an order is meaningful.
9. **Decision history** (`decision-history.json`).
   - **Earlier off:** Biome's action was off in v5 (2025-06), and ESLint's rule was off in V7 (2025-12).
   - **Now on, everywhere.** Both came on with the every-rule policy: Oxlint's explicit list (a63d9c57, 2026-04), ESLint aligned (44f6d7fe, 2026-05), and Biome aligned (2687cf9f, 2026-07).
   - **The only recorded reasons** are the TanStack exceptions (#762, #801) and `package.json` (#728). No issue or PR discusses the rule itself.
