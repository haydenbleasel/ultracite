# Security lint rules in real TypeScript codebases: measurement report

The data behind `/research/security-rules`, measured on 2026-10-10. Generated tables are in `tables.md`. The machine-readable results are:

- `inventory.json`, `rule-census.json` and `rule-census.md`
- `linters.json` (the calibration matrix, and ESLint and Biome on the corpus)
- `sink-census.json`, `sample.json` and `classifications.json`
- `advisories.json`, `advisory-classifications.json` and `advisory-fixes.json`

The agent-experiment subjects are in `corpus/examples/security-rules/`. Everything is regenerated by the scripts in `research/corpus/scripts/security-*.cjs` (see §9).

"Security rule" here means a rule whose own documentation frames it as preventing a vulnerability: code injection, XSS, tabnabbing, cookies, randomness, secrets, crypto, transport, CORS/CSRF, injection, ReDoS. Rules about deprecated or confusing language features (`no-caller`, `no-proto`, `no-with`) aren't counted. The catalogue is in `security-lib.cjs`. The inventory script checks the presets against it, and lists any security-sounding rule it doesn't contain for review (`reviewedNotSecurity`).

## TL;DR

- **Corpus.** The same 8 codebases, SHAs and 3,333 files (694,309 lines) as the earlier reports. Ultracite's own CLI is reported separately.

- **What Ultracite turns on differs a lot by linter.** Not counting the 18 AWS CDK rules:
  - Oxlint's default presets (core + react) enable 12 security rules, and one of them, `typescript/no-implied-eval`, only runs with `--type-aware`.
  - The opt-in js-plugins preset adds 45: sonarjs, github and 4 of react-doctor's.
  - ESLint's core + react presets enable 66, because they turn on every non-deprecated sonarjs, github and unicorn rule. Type-aware adds 3.
  - Biome enables 6 and turns `noSecrets` off.
  - 12 rules are on in ESLint but in no Oxlint preset, including `unicorn/no-unsafe-dom-html`, `sonarjs/slow-regex` and `sonarjs/sql-queries`.

- **How often they fire.** With in-file suppressions honoured:
  - Oxlint's default presets report 29 security diagnostics in 694,309 lines (0.42 per 10,000), from 6 rules. That's 0.04% of the 76,391 diagnostics the same presets report.
  - With js-plugins, 293 (4.2 per 10,000; 0.33% of all diagnostics). The total is dominated by `sonarjs/super-linear-regex` (107), `github/no-inner-html` (66) and `sonarjs/no-clear-text-protocols` (31).
  - 56 of the 75 security rules Oxlint can run never fire.
  - Only one security diagnostic is suppressed in the corpus, and by a file-wide `/* eslint-disable */`. These projects don't run these rules, so there is nothing to suppress.

- **A syntactic census finds 96 injection sinks.** There is no `eval` and no string timer. There are:
  - 6 Function constructors (3 of them through `const F = Function`) and 2 `node:vm` calls
  - 62 `innerHTML`/`srcDoc` writes and 2 other HTML-parsing methods
  - 14 `dangerouslySetInnerHTML`, 6 script elements and 4 `document.cookie` writes

  The census also finds 23 `Math.random()`, 32 `target="_blank"`/`window.open`, 7 `javascript:` strings, 13 secret-looking literals and 33 IP literals.

- **What flows into the 96 sinks**, classified by hand:
  - 53 constants (55%), 15 internally generated and escaped (16%), 26 developer- or build-controlled (27%), 2 possibly user-controlled (2%) and none sanitized.
  - A blind second rater agreed on 24 of 25 injection sites (κ = 0.90).

- **What the rules see of those 96.**
  - Oxlint's default presets report 21, none of them user-controlled.
  - Oxlint with js-plugins reports 92 and ESLint 94. Each includes one of the two user-controlled sinks: an `innerHTML` in Astro's dev toolbar, fed from the astro.build API. The other, an Excalidraw `srcDoc` of AI-generated HTML, isn't reported by anything.
  - Biome reports 18.
  - The rules can't tell the 1 sink worth reviewing from the 91 that aren't.

- **The non-injection rules are all noise on this corpus.**
  - `sonarjs/pseudo-random` flags all 23 `Math.random()` calls, and none is security-sensitive.
  - `react/jsx-no-target-blank` flags 6 links that already have `rel="noopener"`, and misses the one link without it, which is set through a DOM property.
  - `sonarjs/no-hardcoded-ip` flags 2 loopback constants.
  - The secrets rules find nothing, and there's nothing to find: 0 real secrets in 46 candidates.
  - Biome's `noSecrets`, which Ultracite turns off, would add 468 diagnostics. A seeded sample of 60 contains no secrets.

- **Real vulnerabilities: 255 published advisories (2017 to 2026)** for Next.js (74), VS Code (54), Hono (52), Astro (44), Vite (25), Excalidraw (3), tRPC (2) and Zod (1).
  - **Flagged: 2 of the 226 that can be judged (0.9%).** Both are ReDoS: Zod's email regex, caught by `sonarjs/slow-regex` (ESLint only), and Hono's CORS header split, caught by `sonarjs/super-linear-regex`.
  - **Sink-only: 2 more.** A rule fires on the sink but can't see the bug: Next.js's `beforeInteractive` XSS (`react/no-danger`) and a launch-editor command injection (`sonarjs/no-os-command-from-path`).
  - **Not flagged: 222. Unknown: 29**, mostly terse MSRC entries.
  - **Oxlint's default presets flag none of the 255.**
  - **Fix commits.** In 25 of them, linted before and after, no security rule fires on a removed line of any of the 15 XSS fixes. The vulnerable code was a missing `escape()`, `JSON.stringify` inside `<script>`, an unvalidated attribute name or a `data:` URL allowlist.

- **Calibration (136 cases).** Oxlint's default presets catch 32, 69 with js-plugins and 74 with type-aware too. ESLint catches 80 (83 type-aware) and Biome 24.
  - Every linter misses `window["ev" + "al"]`, `self.eval`, `Function.prototype.constructor`, `Reflect.construct(Function, …)` and `el["inner" + "HTML"]`. They also miss `Object.assign(el, { innerHTML })`, a `dangerouslySetInnerHTML` passed in a spread, a `javascript:` URL split across a concatenation, and any URL or HTML that arrives in a variable.
  - **An Ultracite bug.** In the Oxlint config `ultracite init` generates, `no-implied-eval` never fires and `no-eval` misses `window.eval`. Core's `env: { browser: true }` isn't inherited through `extends`, and the generated root config doesn't re-declare it. Re-declaring it restores both (§7).

## 3. Method

### 3.1 Inventory (`security-inventory.cjs`)

The script reads the presets themselves:

- **Oxlint:** `core`, `react` and `js-plugins` `index.mjs`, plus the `oxlint --rules` catalogue for which rules exist and which are type-aware.
- **ESLint:** `core`, `type-aware` and `react` `eslint.config.mjs`, merging only the blocks that apply to ordinary source files.
- **Biome:** `core` and `react` `biome.jsonc`, plus `biome explain` for each rule's recommended flag. The core preset doesn't set `recommended: false`, so Biome's recommended rules are on unless the preset turns them off.

For react-doctor, the security set is its own `Security` category (56 rules), plus `no-document-write`, which react-doctor files under Performance.

### 3.2 Rule census (`security-census.cjs` → `rule-census.cjs`)

The census used the core, react and js-plugins presets in the census's two modes:

- **reported:** in-file disable comments honoured.
- **raw:** every `eslint-`/`oxlint-` disable directive neutralised, 444 of them.

The focus rules are every security rule those presets enable (75). Type-aware rules don't run here, so `typescript/no-implied-eval` counts 0.

The `core + react` rules report 76,391 diagnostics, exactly as in the escape-hatch post's census.

### 3.3 Three linters on the corpus (`security-linters.cjs --corpus`)

ESLint and Biome ran on the census's raw mirror with the security rules. Per-rule counts are compared with Oxlint's raw counts, and every hit is kept for the sink join.

### 3.4 Sink census (`security-sink-census.cjs`)

Every file is parsed with typescript-estree (syntax only). Sinks are recorded by kind and sub-kind:

- **Code execution:**
  - `eval`: direct, `window`/`globalThis`/`self`/`global`/`top`/`parent`/`frames` `.eval`, indirect `(0, eval)`, and `eval` used as a value.
  - The Function constructor: `new Function`, `Function()`, `global.Function`, `.constructor` of a function, and calls through a local alias such as `const F = Function; new F(…)`, recorded at the call.
  - Timers whose first argument is a string literal, template or concatenation.
  - The `node:vm` run functions and `new Script`.
- **HTML:**
  - Assignments to `innerHTML`/`outerHTML`/`srcdoc` (static names, including `el["innerHTML"]`).
  - `insertAdjacentHTML`, `createContextualFragment`, `setHTMLUnsafe` and `parseHTMLUnsafe`.
  - `document.write`/`writeln` and `setAttribute("srcdoc", …)`.
  - JSX `srcDoc`.
  - `dangerouslySetInnerHTML`, as a JSX prop or an object-literal property.
  - `document.createElement("script")`.
  - Reads of `innerHTML` are counted as context.
- **URLs:** strings, template parts and regexes containing `javascript:`.
- **Cookies:** writes to `document.cookie`; reads are counted as context.
- **Randomness:** `Math.random()`. Secure crypto random calls are counted as context.
- **Links:** JSX `target="_blank"`, with the element, `rel`, `href` kind and spread props; `.target = "_blank"`; `setAttribute("target", "_blank")`; and `window.open`.
- **Secrets:**
  - String literals of 6 or more characters with no whitespace, under a name matching password, pwd, secret, token, api key, private key, credential, auth key, access key or signing key.
  - Literals matching known secret formats.
  - URLs with embedded credentials.
  - IPv4 and IPv6 literals, classified by range.

The heuristics are deliberately broad. The hand classification separates the real ones.

A site is "seen" by a linter when a security rule expected for its kind (`EXPECTED` in the script) reports on a line the site spans. Oxlint is joined in raw and reported mode. Security-rule hits that land on no sink are listed so each can be explained.

### 3.5 Hand classification (`security-sample.cjs`, `classifications.json`)

There are few enough sinks to classify all of them: 96 injection, 7 `javascript:`, 23 randomness, 32 link and 46 secret/IP sites. A seeded sample (seed 20261010, drawn from a sorted list) of 60 of the 468 Biome `noSecrets` hits is added.

| Group | Question | Categories |
| --- | --- | --- |
| injection | What flows into the sink? | `constant`; `escaped` (generated internally and escaped/serialized for the context); `sanitized`; `trusted-dev` (developer- or build-controlled: config, compiled code, the framework's own chunks); `user-controlled` (could carry attacker data at runtime without escaping) |
| javascript-url | A `javascript:` URL used, or code defending against one? | `sink`, `defense` |
| randomness | What is the random value used for? | `security-sensitive`, `unique-id`, `jitter-sampling`, `visual-or-dev`; plus `needsCsprng` |
| links | Can the opened page reach `window.opener`? | `protected`, `unprotected-internal`, `unprotected-external` |
| secrets-ips | A hardcoded credential, or a meaningful address? | `real-secret`, `public-or-placeholder`, `not-a-secret`, `local-address`, `not-an-ip`, `public-address` |
| nosecrets | Is the flagged string a secret? | `real-secret`, `not-a-secret` |

**First pass.** Claude subagents did the first pass, reading the worksheet (code context and a permalink per site) and the repo files read-only. They traced values one or two calls back, and gave a source, a note and a confidence for each site.

**Second pass.** The lead agent (also Claude) re-labelled a seeded subset blind, before reading any first-pass label. The subset was 10 per group (seed 7), plus a top-up of 15 injection sites (seed 8). The top-up excluded every id the first rater's summary had named.

| Group | Pairs | Same category | Cohen's κ |
| --- | ---: | ---: | ---: |
| injection | 25 | 24 | 0.90 |
| randomness | 10 | 10 | 1.00 |
| secrets-ips | 10 | 10 | 1.00 |
| javascript-url, links, nosecrets | 7, 10, 10 | all | undefined (one category each) |
| overall | 72 | 71 | 0.98 |

The one disagreement is Astro's button style template (`astro:047`). The first rater read the setters and found that each interpolated value is checked against a fixed list, so `constant`. The second rater, seeing only the template, said `trusted-dev`. The first label stands. Both raters are Claude models, so this measures how consistently the codebook applies, not human judgment.

### 3.6 Advisories (`security-advisories.cjs`, `security-advisory-fixes.cjs`)

**Fetching.** `gh api` fetched, on 2026-10-10:

- Each repo's published repository advisories.
- The global advisory database by npm package. The packages were each project's own (next, vite, astro and its adapters, hono, @trpc/*, zod, @excalidraw/excalidraw) plus any npm package a repository advisory names.

Global-only advisories for a package the project doesn't publish (vite-plus) were dropped. Withdrawn advisories were dropped too.

VS Code publishes no npm package, so it has only repository advisories (54, mostly MSRC entries without CWEs). De-duplicated by GHSA id, that leaves 255.

**Classification.** Each advisory was classified by the lead agent:

- **Class:** from its CWEs and summary (codebook in `advisory-classifications.json`).
- **Lint verdict:**
  - `flagged`: a rule in an Ultracite preset reports the vulnerable construct, and doing what it asks removes the vulnerability.
  - `sink-only`: a rule reports the sink or line, but not the defect.
  - `not-flagged`: nothing reports the vulnerable code; the defect is a missing or wrong check, escape, canonicalization, limit or configuration.
  - `unknown`: too little detail.

**Fix commits.** For 25 fix commits, `security-advisory-fixes.cjs` downloaded the changed source files (tests excluded) before and after the fix. The commits are:

- every XSS or HTML-injection advisory whose advisory links a fix commit (15 commits, 16 advisories);
- the 4 injection-class advisories with a linked fix;
- both ReDoS advisories;
- 4 contrast cases: JWT, timing and two prototype-pollution fixes.

It linted both versions with all three linters' security rules and recorded hits on lines the fix removed.

Advisory text is data; nothing from it or from the downloaded files was executed.

### 3.7 Calibration (`calibration/security-rules/`)

The calibration has 136 hand-written cases in three files, with a strict `tsconfig.json` for the type-aware runs:

- `sinks.ts`: code execution, HTML, URLs, cookies and storage, randomness, secrets, messaging, transport and regexes.
- `components.tsx`: JSX.
- `server.ts`: Node crypto and TLS, Express, cookies, SQL, child processes, `vm`, file system.

Each case starts with a `// ID: description` comment. A diagnostic maps to the case it falls in.

They ran through 8 configurations:

- Oxlint: core + react (Ultracite's default); the same with core's `env` re-declared on the root (§7); + js-plugins; + `--type-aware`.
- ESLint: core + react; + type-aware.
- Biome: Ultracite's config; the security rules it leaves off.

### 4.7 What would catch more (not run here)

These are noted, not measured: none is installed here, and nothing was installed.

- **`eslint-plugin-no-unsanitized`** flags HTML-sink assignments and calls whose argument isn't a literal or an approved escaper. That would separate the 39 constant `innerHTML` writes from the rest. It is still syntactic, so computed names, `Reflect.set` and `Object.assign` pass.
- **Trusted Types** (CSP `require-trusted-types-for 'script'`) make the browser reject plain strings at the DOM XSS sinks themselves: `innerHTML`, `outerHTML`, `insertAdjacentHTML`, `srcdoc`, `document.write`, `eval`, `new Function`, string timers, `script.src`. That covers every evasion above at runtime.
- **Type-aware and taint analysis** (CodeQL, Semgrep taint mode) is what follows a value from request to sink. Ten of the 16 XSS fixes in §4.5 add an escape or validation of a value on its way to the output.

Check current browser support and the plugin's documentation before quoting either.

## 5. Findings worth stating carefully

- **The rules mostly flag sinks, not vulnerabilities.** ESLint flags 94 of 96 injection sinks, and 1 is possibly user-controlled.
- **Real vulnerabilities in these projects are logic bugs.** 222 of 226 judged advisories are not flagged; the 2 that are, are regexes. XSS fixes add an escape, a validation or a header, and don't remove a sink.
- **The default Oxlint config sees very little.** 29 hits in 694k lines, 0 user-controlled. The `innerHTML`, `Math.random`, crypto and ReDoS coverage is in opt-in js-plugins, and the broadest HTML coverage (`unicorn/no-unsafe-dom-html`) is ESLint-only.
- **Evasions are easy, and some are idiomatic.** Zod writes `const F = Function` in three places, two of them next to comments about CSP, and doesn't trip `no-new-func`. A ref's `innerHTML` replaces `dangerouslySetInnerHTML` and leaves Biome and Oxlint's defaults silent.
- **The rules that fire are mostly noise.** `pseudo-random` 23/23, `jsx-no-target-blank` 6/6, `no-hardcoded-ip` 2/2 and `require-post-message-target-origin` 1/1 (6/6 in ESLint) all flag only code that's fine. Biome's `noSecrets` found 0 secrets in 60 sampled hits.

## 6. Caveats

- **Snapshot.** The repos are at their 2026-10-10 HEADs, so the corpus is post-fix for most advisories. The fix-commit linting covers pre-fix code for 25 commits.
- **Frameworks and libraries, not apps.** App code likely has more user-controlled sinks and more Express and crypto code, where sonarjs's server rules apply.
- **Slices.** VS Code's slice has no DOM code, and Next.js is 40% of the lines.
- **The classification is judgment.** LLM raters, a written codebook, code context and repo files. "user-controlled" means could carry attacker data, not exploitable. The second pass covered 25 of 96 injection sites; the noSecrets sample is 60 of 468.
- **Advisory verdicts are judgment too.** 228 rest on the summary and description, 26 on the linted fix commit, and one on the advisory plus the corpus code (gx5p, whose fix isn't linked). "Not flagged" for a summary-only advisory means no rule in the presets targets that class of defect. The 29 `unknown` are mostly VS Code MSRC entries.
- **The global advisory query** is by npm package. VS Code CVEs without a GitHub advisory aren't included.
- **Calibration cases are hand-written** and say nothing about frequency. Some outcomes depend on how a case is written:
  - sonarjs's entropy threshold;
  - its example-key allowlist;
  - `fs.chmodSync` vs a named import;
  - V24 (`sql-queries` on a `pg` query). It fires without types, and is silent with types because `pg` isn't installed.
- **react-doctor skips `examples/` paths.** That's why its `no-eval` hit on subject s1 is missing in place.
- **The census ran js-plugins without `jsPluginSettings`.** That only affects react-doctor's ported rule mode, not any security rule. The calibration and advisory runs set it.

## 7. Notes on Ultracite itself

These are raised for Hayden rather than fixed; this report changes no preset.

1. **Oxlint's `env` isn't inherited through `extends`.**
   - With Oxlint 1.86.0, `extends: [core]` reports 0 `no-implied-eval` on three string timers, and adding `env: core.env` reports 3.
   - The config `ultracite init` generates (`packages/cli/src/linters/oxlint.ts`) re-declares `ignorePatterns`, `jsPlugins` and `settings` for the same reason, but not `env`.
   - The effect: `no-implied-eval` never fires on `setTimeout("…")`, and `no-eval` misses `window.eval`. On this corpus the effect is nil, because there are no such calls.
   - Other env-dependent rules weren't checked.
2. **Oxlint js-plugins omits 4 sonarjs rules ESLint core keeps:** `slow-regex`, `sql-queries`, `disabled-auto-escaping` and `dompurify-unsafe-config`, which ESLint's `worksWithoutTypes` list covers. `slow-regex` is the only rule that would have caught the Zod advisory.
3. **There is no Oxlint equivalent of `unicorn/no-unsafe-dom-html`.** Oxlint gets nothing for `outerHTML`, `insertAdjacentHTML`, `srcdoc`, `createContextualFragment` or `setHTMLUnsafe`. It gets `document.write` only through react-doctor in js-plugins.
4. **react-doctor parity.** ESLint enables 8 of its security rules, Oxlint 4, and 49 are on in no preset.
5. **`react/jsx-no-target-blank` and Biome's `noBlankTarget` disagree** on `rel="noopener"`, internal links and forms.
6. **Biome `noSecrets` stays off with good reason:** 468 hits, 0 of 60 sampled are secrets. The recorded reason is the next-forge sync.
7. **The default Oxlint security set is 12 rules,** and most coverage needs opt-in js-plugins. Whether that's intended is a positioning question for the post, not a bug.
