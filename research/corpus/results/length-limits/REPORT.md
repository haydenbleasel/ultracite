# Length limits as lint rules: measurement report

The data behind the post on length limits, measured on 2026-10-25. Generated tables are in `tables.md`. The machine-readable results are:

- `rules.json`: what Ultracite's presets set for every length and structure rule, per linter and preset, each rule's defaults, Biome's severities, the agent prompt's lines, and the preset inconsistencies
- `census.json`: the inventory, every function and file measured the way each rule counts, per repo and pooled, source and tests apart (rows in `out/length-limits/census/`)
- `corpus-lint.json`: what each limit reports in Oxlint, ESLint, Biome and SonarJS at its default and the common settings, function-by-function agreement, and every linter's messages
- `rule-census.json`, `rule-census.md`: the shared Oxlint census with Ultracite's core, react and js-plugins presets
- `calibration.json`: 42 hand-written cases through every linter and option
- `format.json`: the corpus formatted with Oxfmt (Ultracite's preset, then printWidth 100 and 120) and measured again
- `history.json`, `history-check.json`: changes and bug fixes per function over three years, the regressions, the hand check of the bug-fix heuristic
- `complexity.json`: length against cognitive complexity
- `markers.json`: the projects' own lint settings and disable comments for these rules
- `sample.json`, `classifications.json`: the hand classification, both raters
- `agent-runs.json`: length in the agent experiment's committed runs
- `decision-history.json`: how Ultracite came to turn the size limits off

The agent-experiment subjects are in `corpus/examples/length-limits/`. Everything is regenerated by `research/corpus/scripts/length-*.cjs` (§9).

Terms:

- **Function:** what ESLint's `:function` selector matches (declarations, expressions, arrows; so methods, accessors, constructors, class-field arrows, callbacks, IIFEs). Bodiless TypeScript signatures are counted apart.
- **Lines:** max-lines-per-function's count, physical lines from a method's key (decorators included) or a function's start to its end. **Code lines** skip blank and comment-only lines. **Biome lines** are noExcessiveLinesPerFunction's count, which is different (§4.4).
- **Size limits:** max-lines, max-lines-per-function, max-statements, max-params (and @typescript-eslint/max-params), max-depth, and their Biome and SonarJS equivalents, all off in Ultracite. **Structural limits:** max-nested-callbacks, max-classes-per-file, sonarjs/max-switch-cases and max-union-size, which Ultracite keeps on.
- **Corpus, React set, external:** the eight repos of every topic; the four React codebases from the accessibility post; both together. Ultracite's CLI is listed apart and never pooled.

The calibration finds a few more differences: decorated methods are counted from `(`, directives aren't statements, and a brace-less nested `if` doesn't add depth.

- **Length and bugs, size as the confound** (eight corpus repos, three years, 29,787 functions):
  - **Per function, longer means more fixes:** 10% of 1–10-line functions changed by a bug-fix commit, 44% of 51–100, 74% over 200.
  - **Per line, fewer:** 1.52 fixes per 100 line-years at 1–10 lines, 0.89 at 51–100, 0.76 over 200. Fixes are 24–25% of changes up to 100 lines, 19.5% over 200.

## 3. Method

### 3.1 The inventory (`length-census.cjs`, `length-lib.cjs`)

One ESLint `Linter` pass per file runs a census rule plus the real rules at threshold 0, so every measured function reports its count. The census reimplements each count from the rule's source:

- **Lines:** ESLint's (key or start; blank and comment-only lines), Oxlint's (node span), SonarJS's (lines of code; component and IIFE exemptions), Biome's (below).
- **Statements:** every block's statements, nested functions excluded, directives and empty statements included.
- **Parameters:** with and without `this` (ESLint counts `this` unless typed `void`), and bodiless signatures.
- **Depth:** max-depth per function (`else if` doesn't nest), and S134's nesting, which crosses function boundaries.
- **Callbacks:** ESLint's, Oxlint's and Biome's definitions of a callback.
- **Kinds:** IIFEs, callbacks and callee, components, test callbacks, dispatchers, data and nested lines, free variables.
- **Complexity:** cognitive and cyclomatic, joined by report location.

**Result: 111,243 functions; 0 mismatches** between census and the real rules for max-lines-per-function (and three option variants), max-statements, max-params, @typescript-eslint/max-params, max-depth, max-nested-callbacks, max-lines (and two variants), max-classes-per-file, sonarjs/max-lines-per-function, max-lines, max-switch-cases, max-union-size and nested-control-flow; 0 unmatched reports; 0 parse errors.

**Biome's line count, reimplemented** from `no_excessive_lines_per_function.rs` at 2.6.3:

- **The count:** for every body token except `{` and `}`, the newlines in its leading trivia. Breaks inside a comment are one trivia piece, JSX text is a token, and an arrow's parenthesised expression body includes its parentheses.
- **Check:** it predicts every Biome count in the corpus.
- **`biomeLinesExplained`** assigns each line break to one category (counted, head, brace, comment, JSX text, string); the categories sum to ESLint's count minus one.

### 3.2 The linters (`length-linters.cjs`, `length-disagreements.cjs`)

- **Runs.** Oxlint each rule at 0, default and the settings: max-lines-per-function 50/100, max-statements 10/20/30, max-params 3/4/5/7, max-lines 300/500/1000, max-depth 4, max-nested-callbacks 10, max-classes-per-file 1. Biome at the equivalent settings, plus noExcessiveNestedCallbacks 5 and 10. ESLint and SonarJS for real at the defaults and settings.
- **Joins.** Every diagnostic joins exactly to a function, its parameter list or its block, or to nothing.
  - **Oxlint:** byte offsets converted to UTF-16.
  - **Biome:** code-point columns.
  - **Type-level reports** (function types, declared functions) are counted apart.
- **Checks.** ESLint's flags equal the census counts over each threshold in every repo (0 mismatches); Biome's counts equal the reimplementation.
- **Agreement.** Every function two implementations count or flag differently gets a reason, an example and a permalink.

### 3.3 The formatter (`length-format.cjs`)

Copies are formatted three times, parsed and measured again. Functions are matched by order, kind, node type and depth (names can change, e.g. a callee's quotes). Every function matched and every file parsed.

### 3.4 History (`length-history.cjs`, `length-history-check.cjs`)

- **Tracking:** each source function's line range is followed back through three years of mainline commits (`git log --first-parent --diff-merges=first-parent -M -w -p -U0`, as `git log -L` does), through renames.
  - **Exclusions:** whitespace-only changes are ignored, and the commit that creates a function isn't a change to it.
- **Attribution:** to the innermost function containing the changed line. Commits touching over 50 files in scope (82 in all) count for nobody.
- **Bug fixes:** conventional `fix:`/`fix(scope):` subjects or fix/bug/regression/crash/broken/incorrect/wrong words, excluding reverts, bumps and "fix typo/lint/tests/CI/docs/types". This is the keyword convention from SZZ ([Śliwerski, Zimmermann and Zeller 2005](https://doi.org/10.1145/1083142.1083147)). One rater checked 60 commits the heuristic calls fixes and 40 it doesn't.
- **Analysis:** functions with at least 30 days of exposure (29,787).
  - **Rates** per function and per line-year.
  - **Logistic regressions** of "changed by a fix" on log own lines (outside nested functions), each metric, log exposure and repo fixed effects, with file-clustered SEs; also among changed functions with log changes, and top-level functions on total lines.
  - **Why size is controlled:** a metric–fault association can be a size association ([El Emam et al. 2001](https://doi.org/10.1109/32.935855); [Gil and Lalouche 2017](https://doi.org/10.1007/s10664-017-9513-5)).
- **Lost:** moves between files look like births; survivors only; wholesale rewrites in the same range count as the same function.

### 3.5–3.10

- **Complexity** (`length-complexity.cjs`): Spearman with average ranks; overlap with Ultracite's threshold (20, read from `packages/cli/config`); subtree scores including nested functions.
- **Policy** (`length-markers.cjs`): every ESLint, Biome and Oxlint config at each pinned commit (`git show`; working tree for the React set), skipping test, fixture, example, template and docs paths, and only Ultracite's root config. Every line naming these rules, with `git log -S` for when it was added, and every disable comment naming one.
- **Hand classification** (`length-sample.cjs`, seed 20261025):
  - **Samples:** 100 functions over 50 lines, stratified by repo and shape (at most one per file), and 30 with five or more parameters.
  - **Long-function fields:** why it's long; whether a reader can follow it end to end as written; whether splitting helps; split points; split cost; whether it's hard for other reasons.
  - **Parameter fields:** swappable neighbours ([Rice et al. 2017](https://doi.org/10.1145/3133928)), whether an options object would help, who owns the signature.
  - **Raters:** rater 1 labelled all 130; rater 2 (separate, blind) a seeded 30 and 10. Both are Claude models. Shares are weighted by stratum.
- **Calibration** (`length-calibration.cjs`): 31 TS, 5 JSX and 4 declaration cases, a four-class file and a printWidth case, through every linter at minimum thresholds, with option variants and at defaults.
- **Agent runs** (`length-agent-runs.cjs`): 216 runs plus 24 superseded, measured before and after and per attempt; functions matched by name and kind.
- **Subjects** (`length-examples.cjs`, `length-oracle.cjs`): verbatim lines checked against the clones, tsc with stubs, every linter at defaults before and after Oxfmt, a behaviour oracle, and a reader-cost measure for every variant: functions and entry lines afterwards, each helper's parameters, lines and call sites, and whether helpers appear in the order the entry calls them (a proxy for "still reads top to bottom").

Of every line break in the functions Biome measures, it counts 71%:

- **In front of `{` or `}`:** 15.2%
- **Inside JSX text:** 8.2%

Biome's noExcessiveNestedCallbacks reports only the first callback over the limit and suppresses those nested in it (source at 2.6.3), where ESLint and Oxlint report every one.

- **Among changed functions** (12,710), with the number of changes controlled, own lines are 1.10 [1.05, 1.15]. With a metric added they drop to about 1: longer functions aren't fixed more often than their churn predicts.
- **Top-level functions on total lines** show the same pattern, with somewhat larger metric terms (statements 1.37, cyclomatic 1.35).
- **Partial Spearman** with fixes per year, on own lines: statements −0.009, parameters 0.003, depth 0.018, cognitive 0.045, cyclomatic 0.065.
- **History is uneven.** Every one of zod's measured functions was born in the window. Hono, Vite and Excalidraw call over half their mainline commits fixes; VS Code calls 15.5%.

## 5. Findings worth stating carefully

- **The line limits measure formatting as much as code.**
  - **Across linters:** the same function is 72 lines to ESLint and Oxlint and 66 to Biome; a component is 54 or 4.
  - **Across formatting:** Ultracite's formatter adds up to a third more lines and pushes 6–12% more functions over 50.
  - **Statements don't move** with formatting.
- **Most of what a length limit flags is fine:** 70% of functions over 50 read end to end; splitting fully helps 17%. The biggest groups are JSX markup and one task's steps.
- **Long functions aren't worse per line.** They get more fixes because they have more lines; per line-year they get fewer. With size controlled, statements and depth predict nothing more, and cognitive and cyclomatic complexity a little. This is consistent with the size confounding El Emam et al. and Gil and Lalouche describe, and says nothing about readability.
- **Length overlaps complexity at the top only:** 91% of functions over the cognitive limit are long, but 83% of long functions are within it. A cognitive limit already catches the long functions that are hard to follow; a length limit adds the long flat ones.
- **Splits that satisfy the limit cost a reader.** In all three subjects every limit-clearing edit adds single-use helpers. In A and C they take 4–11 values and trip max-params, and formatting A's options-object versions pushes the helper back over 50.
- **The structural limits Ultracite keeps on** almost never fire (0 nested-callback reports, 2 switch-case reports); max-classes-per-file flags 177 files.

## 6. Caveats

- **Snapshot and mix.** HEADs from 2026-10. Next.js is about a fifth of source functions and Supabase over a third, so per-repo values are given. Tests are only those in the clones.
- **Measured off.** No project except tRPC (max-params) and React Aria (max-depth warn) wrote code to these limits; a codebase that enforces one is shaped by it.
- **History.**
  - **The heuristic:** 74% precise, missing about 15%, on one rater's reading of messages and file lists; repos differ widely in how often they say "fix".
  - **Attribution** is by line, so a call-site fix counts for the caller.
  - **Sample:** survivors only, eight repos, three years; moves reset history; SEs are clustered by file, not commit.
  - **Associations, not effects.**
- **Raters are Claude models.** κ is 0.91–0.96 on the main fields and 0.42 on split cost; the parameter subset is small (10).
- **The reimplementations are checked, not proven.** They match every report at these versions.
- **Biome's statements rule is nursery** (2.6.0).
- **The agent runs** come from other topics, whose subjects weren't about length.

## 7. Notes on Ultracite itself (for Hayden, not fixed)

1. **Biome doesn't enforce one class per file.** `style/noExcessiveClassesPerFile` (since 2.3.12, default 1) is set to `"off"` in `biome/core`, added with the Biome 2.5.2 upgrade (aea7fc06, 2026-07-04) without a comment. max-classes-per-file is `"error"` (1) in the Oxlint and ESLint presets. The calibration's four-class file gets no Biome report; the corpus has 177 files the other two would report.
2. **sonarjs/nested-control-flow isn't a duplicate of max-depth,** as the comments say. It carries nesting across function boundaries and defaults to 3 rather than 4 (310 functions differ; calibration L21). Off may still be right, but the stated reason is wrong.
3. **"Same" limits differ across presets.**
   - **noExcessiveNestedCallbacks** reports only the outermost callback over 10; Oxlint also counts IIFEs and casts as callbacks.
   - **useMaxParams** (off) would skip `export default function` and accessors and count `this: void`.
   - **The parity script** compares ESLint with Oxlint only.
4. **@typescript-eslint/max-params was on at 3** for TS files from V7 (2025-12-28) until efa80e8c (2026-09-28), because the ESLint preset enabled every typescript-eslint rule.
5. **The prompt and length diagnostics.** The prompt asks for "the minimal change" and the help says "split". For a length diagnostic the honest minimal change is often none, which "Left for review" allows.
6. **Small things.**
   - **Oxlint messages:** max-lines puts the maximum in the help; max-classes-per-file's message has no full stop.
   - **The Vite license file:** `examples/licenses/vite-LICENSE` (another topic's) has Vite's older copyright line; this topic adds `vite-3b72997d-LICENSE` from the pinned commit.
