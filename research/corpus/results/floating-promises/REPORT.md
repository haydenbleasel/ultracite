# Floating promises and async mistakes in real TypeScript codebases: measurement report

The data behind `/research/floating-promises`, measured on 2026-10-10. Generated tables are in `tables.md`. The machine-readable results are `rule-inventory.json`, `rule-census.json`, `async-census.json`, `typed-census.json`, `repo-configs.json`, `linters.json`, `detector-check.json`, `detector-review.json`, `sample.json`, `classifications.json` and `history.json`, plus `examples/floating-promises/examples.json`. Everything is regenerated by the scripts in `research/corpus/scripts/` (see §9).

At the time, Ultracite's Oxlint core preset enabled the type-aware `typescript/no-floating-promises`, `no-misused-promises`, `await-thenable`, `return-await` (`always`), `promise-function-async`, `strict-void-return`, `prefer-promise-reject-errors` and `use-unknown-in-catch-callback-variable`, which only run with `--type-aware`. Syntactically it enabled ESLint's base `require-await` (with `typescript/require-await` off), `no-await-in-loop`, `no-async-promise-executor`, `no-promise-executor-return`, `no-void` with `allowAsStatement`, 13 `promise/*` rules (including `prefer-await-to-then`; `always-return` and `catch-or-return` off) and 7 `unicorn/*` promise rules, including `no-array-for-each`. The ESLint preset enables the same typescript-eslint rules in its type-aware preset, where it swaps base `require-await` for `@typescript-eslint/require-await`. Biome's core preset enables `noAwaitInLoops`, `useAwait`, `noAsyncPromiseExecutor`, `noNestedPromises`, `noThenProperty`, `noForEach` and `noVoid`. It does not enable Biome's nursery `noFloatingPromises` or `noMisusedPromises` (see §8).

## TL;DR

- **Corpus.** The same 8 codebases and 3,333 files (694,309 lines) as the earlier reports, at the same SHAs. The type-aware rules ran on the 3,320 TypeScript files.
- **Floating promises are common where the rule is off, and absent where it's on.** typescript-eslint's `no-floating-promises` fires 260 times (3.7 per 10,000 lines) in 130 files, and `no-misused-promises` 127 times (1.8 per 10,000). tRPC, the one repo that enforces `no-floating-promises` on its source, has 0. Astro switches it off for source files "until we have the bandwidth to address all the errors" and has 37, Next.js has it off with "TODO: enable in follow-up PR" and has 132, and Vite turns it off and has 27.
- **These are lower bounds for 6 of 8 repos.** The clones have no `node_modules`, so 9–31% of imports don't resolve (outside zod and hono) and 10–22% of bare call statements are typed `any` or an error type, which the rule can't judge. Zod and hono resolve fully.
- **Maintainers almost never suppress these rules.** Only 2 suppression comments in the corpus name any async rule (both `no-async-promise-executor`, in hono). Counting with suppressions honoured and neutralised gives the same numbers for every other async rule.
- **Most floating promises are deliberate, but a third can lose something** (68 sites hand-classified, 12 per repo where available):
  - 43 (63%) are fire-and-forget by design with nothing to lose, but undocumented. 3 (4%) say so at the site. 22 (32%; 27% weighted by repo size) are latent bugs: 18 lose an error and 4 also break ordering.
  - Of the 22, 6 only duplicate an error that's already reported elsewhere, leaving 16 (24%) that lose something outright. 6 of the 68 aren't promises at runtime at all (the declared type over-approximates).
  - A blind second pass on 20 agreed on all 20 (κ = 1.0).
- **Two-thirds of `await` in loops must stay sequential** (76 sites): 45% depend on the previous iteration (streams, cursors, polling, retries), 21% need ordering or an early exit, and 1% throttle deliberately. 18% could use `Promise.all`, and 11% await promises that were already started. Only 16% say why at the loop. The second pass agreed on 18 of 20 (κ = 0.83).
- **25 confirmed fixed bugs in the 8 repos' history** came from missing `await`s, floating promises, unhandled rejections or `forEach(async …)`. Default `no-floating-promises` or `no-misused-promises` would have flagged 13 of them. The other 12 stored the promise instead of dropping it (7), hid it behind a loose type such as `as any` or `() => unknown` (4), or awaited pre-started promises in a loop (1, which `no-await-in-loop` flags).
- **Oxlint and typescript-eslint agree.** Where tsgolint could load the tsconfig (hono, vite, astro, excalidraw), Oxlint's type-aware `no-floating-promises` matched typescript-eslint line for line on all 121 hits. `no-misused-promises` differed on 1 of 77 (`.finally(async …)`). On the 37 calibration cases the two linters' async rules agree everywhere except `require-await`, where Oxlint runs ESLint's syntactic base rule.
- **What none of the rules see:** a promise stored in a variable or field and never awaited, a `.catch(() => {})` that swallows the error, an async callback where the parameter type returns `unknown`, and a non-`Promise` thenable. TypeScript itself already rejects two cases the lint rules also cover: a promise used as a condition (TS2801) and an async `useEffect`-style callback (TS2345).

## 3. Method

### 3.1 What Ultracite enables (`async-rule-inventory.cjs`)

The script imports each preset as shipped. A rule counts as async if it's in the promise plugin or its name matches promise, await, async, then, floating-promise, misused-promise, forEach, executor, void or callback, minus a hand list of false matches such as `no-misused-new` and `no-floating-decimal`.

- Oxlint's type-awareness comes from `oxlint --rules --format json`.
- ESLint's rule set comes from `calculateConfigForFile` on a `.ts` path, with `core` alone and with `core` + `type-aware`. Type-awareness comes from each rule's `meta.docs.requiresTypeChecking`.
- Biome's comes from the presets' JSONC and the schema. Biome has no type-aware flag, so the rules in its `types` domain (`noFloatingPromises`, `noMisusedPromises`, `useAwaitThenable`) are listed as inference-based.

### 3.2 Rule census (`rule-census.cjs`)

As in the earlier reports: Oxlint over the files as they are (`reported`), then over a mirror with every `eslint-`/`oxlint-` disable directive neutralised (`raw`). The focus rules are the 27 syntactic async and promise rules in the core preset. The type-aware rules always count 0 here and are measured in §3.3.

### 3.3 Type-aware census (`async-typed-census.cjs`)

Type-aware rules need resolved types, and the clones have no `node_modules`. Only zod and hono have no runtime dependencies. Rather than restricting the census to those two, every repo is measured, and a probe rule records how much of each program resolved:

- **Imports resolved:** the share of import and export specifiers for which the checker has a module symbol, including ambient `declare module` declarations.
- **Bare calls typed `any`/error:** the share of `f();` statements whose type is `any` or the error type. These are exactly the statements `no-floating-promises` can't judge.
- **Programme-level diagnostics** (such as TS2688, a `types` entry that isn't installed) and per-file semantic diagnostics by code.

TypeScript resolves modules by walking up directories, and the clones sit inside this repo, so some imports resolve through Ultracite's own `node_modules`, mostly `@types/node` for `node:*` and Node built-ins. The probe records these separately (`topOutside`). They give real Node types, which happen to be what the repos use, but at Ultracite's version. A repo with unresolved imports is marked as a lower bound.

Suppression comments near each hit are checked separately: an `eslint-`/`oxlint-disable` naming the rule, or a blanket one, on the line, the line above, or file-wide. None of the 2,542 type-aware hits had one.

### 3.4 Syntactic census (`async-census.cjs`)

To have numbers that don't depend on resolution, every file is parsed with typescript-estree 8.71.0, syntax only:

- **Floating call:** an expression statement calling a function declared `async`, or annotated to return `Promise`/`PromiseLike`, in the same file. This covers plain calls by name, `this.name()` for methods of a class in the file, and async IIFEs.
- **Floating chain:** a `.then(a)` or `.finally(f)` statement with no rejection handler, and a bare `.catch()` with no argument. As in typescript-eslint, `.finally` is followed back to the promise before it, so `p.catch(h).finally(f)` counts as handled.
- **Async callback:** an async function literal passed straight to a call or `new`, grouped by callee.
- **`.map(async …)`:** grouped by what happens to the array: passed to `Promise.all`/`allSettled`/`race`/`any` directly or through a variable in the same function, returned, awaited directly, a bare statement, stored, or other.
- **`await` in loops:** ESLint's own algorithm. Function bodies and `for await` loops are boundaries, and `for await` nested in a loop and `await using` count. The count equals Oxlint's raw `no-await-in-loop` in every repo (404 pooled).
- **Async functions without `await`:** generators and empty bodies are skipped, as ESLint's `require-await` does. Each is grouped by what it returns and where it sits. The count equals Oxlint's raw `require-await` in every repo (459).
- **Markers:** `void x;` statements by operand, `.catch(h)` and `.then(a, h)` handlers by what `h` does, and suppression comments that name an async rule. A handler is empty (`() => {}`, `() => undefined`), a no-op reference (`noop`), log-only (a body made only of `console.*` or logger calls), a reference to some other handler, or something else.

### 3.5 Detector check (`async-detector-check.cjs`)

The detector's floating sites are matched to typescript-eslint's `no-floating-promises` hits by file and start line, since both report the statement. For each typed hit the detector missed, the script parses the statement and records why syntax couldn't see it.

Every detector-only site was read by hand (`detector-review.json`). The first comparison found 13 detector-only sites. 6 were `.catch(h).finally(f)` chains that typescript-eslint correctly treats as handled. The detector was changed to follow `.finally` back, as typescript-eslint does, and the other 7 were all real floating promises that the typed rule missed because types didn't resolve.

Async callbacks were matched to `no-misused-promises` `voidReturnArgument` hits the same way, by the function's start line.

### 3.6 Three linters (`async-linters.cjs`)

- **Calibration:** 37 cases in `calibration/floating-promises/cases.ts`, with a strict tsconfig (DOM lib, no `types`). Each case starts with a `// #F01:` header, and every diagnostic up to the next header belongs to it, so no diagnostic is unaccounted for. They ran through the TypeScript compiler, Ultracite's presets in all three linters, and Biome's nursery rules. Only async and promise rules from the inventory are kept.
- **Corpus:** the raw mirror ran through ESLint and Biome with the syntactic rules all three linters have, plus Biome's `noFloatingPromises` and `noMisusedPromises`. Every line where Biome's count differs from Oxlint's raw hits is recorded with its code.
- **A Biome gotcha.** Its inference-based rules report nothing when the config is passed with `--config-path` from another directory. They need the config at the root of the linted files, presumably because its type inference scans the project from there. Checked with Biome 2.5.15 on a probe file: 5 hits with the config in place, 0 with `--config-path`. The script copies the config in for the run and deletes it afterwards. Biome's syntactic rules are unaffected.

### 3.7 Sampling and classification (`async-sample.cjs`, `async-merge-labels.cjs`, `async-agreement.cjs`)

- **Populations.** Floating: the union, per repo, of typescript-eslint's `no-floating-promises` and `no-misused-promises` hits and the 7 detector-only sites, deduplicated by line (392 sites). `await` in loops: Oxlint's 404 raw `no-await-in-loop` hits.
- **Sample.** Seed 20261010, up to 12 per repo per kind: 68 floating sites (zod and tRPC have 1 each, VS Code 6) and 76 loop sites (zod 6, Excalidraw 8, VS Code 2). Shares are reported unweighted and weighted by each repo's population.
- **Codebook** (stored in `classifications.json`):
  - Floating: `intentional-documented`, `intentional-undocumented` (nothing to lose, but nothing at the site says so), `latent-bug` (a rejection nothing handles, or later code depending on unfinished work) or `unclear`. Plus `canReject`, `bugKind` and the fix a careful maintainer would make.
  - Loops: `sequential-dependency`, `sequential-ordering` (order or early exit), `sequential-throttle`, `already-concurrent` (the promises were started before the loop), `parallelizable` (only when the rater would propose `Promise.all` in review) or `unclear`. Plus `documented` and `earlyExit`.
- **First pass.** A Claude subagent per kind classified every site from the worksheet: about 19 lines of context, plus the repo files, read-only, to look up callees. The floating pass made about 95 tool calls, the loop pass about 40.
- **Second pass.** The lead agent (also Claude) labelled a seeded subset of 20 per kind blind, from `--print` output and the repo files, before reading the first pass.

| Kind | Same category | Cohen's κ | Same coarse label | Coarse κ |
| --- | ---: | ---: | ---: | ---: |
| floating | 20 of 20 | 1.00 | 20 of 20 | 1.00 |
| `await` in loops | 18 of 20 | 0.83 | 18 of 20 | 0.73 |

The two loop disagreements were close calls:

- **w045** (Astro's types generator): the first pass said parallelizable if the output string is rebuilt in order. The second pass said sequential-ordering, because the loop returns early on an error and builds shared state in order.
- **w067** (Next.js metadata): the first pass said already-concurrent, because the resolver only awaits a promise created outside the loop. The second pass said parallelizable.

Both raters are Claude models, so this measures how consistently the codebook can be applied, not human judgment.

After both passes, two cross-cutting groups were annotated from the evidence and the code:

- **Not a promise at runtime (6 of 68):** an always-sync `MaybeAsync` check, `splice`/`pop` on arrays whose element type includes `Promise`, `process.off`, and `Object.defineProperties` returning the promise the function returns two lines later.
- **Duplicate rejection (6 of the 22 latent bugs):** the same error is also handled, rethrown or reported elsewhere, so the cost is a second "Uncaught (in promise)", not a lost error.

### 3.8 History (`history.json`)

- **Search.** A Claude subagent searched each upstream repo with `gh search commits`, `prs` and `issues` for "missing await", "add missing await", "forgot await", "floating promise", "no-floating-promises", "unhandled rejection", "unhandled promise", "not awaited", "forEach async" and "misused promise", within rate limits.
- **Selection.** It read each candidate's fix diff and kept only merged fixes of a behavioural bug: lost errors, races, crashes, hangs, wrong output or test flakes, not lint cleanups. That left 25 confirmed, 19 rejected and 6 lint-driven changes noted for context.
- **Rule verdicts.** For each bug, it judged from the pre-fix code and the callee types at the parent commit whether default `no-floating-promises` or `no-misused-promises` would have flagged it.
- **Verification.** The lead agent re-fetched all 25 PRs or commits with `gh`. Each is merged, or for the two bare commits, an ancestor of `main` by the compare API. Each patch contains the quoted change.

### 3.9 Agent-experiment subjects (`async-examples.cjs`)

Two real functions with a genuine violation, copied verbatim with their license headers, plus marked stubs for what they need from elsewhere. Each keeps its violation standalone: the same lines are flagged by typescript-eslint and by Oxlint type-aware, and the TypeScript compiler reports 0 diagnostics. See §4.9.

- **Async functions without `await`** (459):
  - 260 (57%) return a call, usually another promise. 115 return a value, 84 return nothing.
  - typescript-eslint's `require-await` allows a function that returns a promise, and flags 227. Oxlint's preset runs ESLint's syntactic base rule, which flags all 459 (§8).

### 4.5 The syntactic detector vs the type-aware rule

| | Sites |

## 6. Findings worth stating carefully

- **The rule is about intent as much as bugs.** Two-thirds of flagged sites are deliberate fire-and-forget with nothing to lose, and almost none say so (3 of 68). The useful outcome for those is an explicit marker (`void`, or a comment), not a code change. A third can lose something, and those are the ones the rule exists for.
- **The rule can't see where the errors go.** It flags an un-awaited call whose callee catches everything exactly like one that can crash Node. Deciding needs the callee, which is why the classifier read it.
- **Missing types silently reduce the count.** A repo missing its dependencies loses floating promises without any error. Here that was 10–22% of bare calls typed `any`, and 7 confirmed misses. Projects that don't install types, or lean on `any`, get less from the rule than its silence suggests.
- **What actually broke in history is often outside the rule's reach.** Half of the 25 real bugs stored the promise or hid it behind `any`/`unknown`. The type-aware rules are necessary but not sufficient.
- **`await` in a loop is usually right.** Only 18% of sampled loops could be parallelized. The rule is better read as "make sure this is sequential on purpose" than "this is slow".

## 7. Caveats

- **Snapshot.** Each repo is at its default-branch HEAD as pinned on 2026-10-10. Next.js is 40% of the pooled lines and 51% of the floating promises.
- **Lower bounds.** Six repos lack their dependencies, and VS Code is a sparse slice whose relative imports into `src/vs/base` don't resolve. Their type-aware counts are lower bounds. The detector found 7 sites the typed rule missed, and nothing measures how many neither found.
- **Ultracite's `node_modules` leaks in.** TypeScript resolves some imports, mostly `@types/node`, through this repo's own `node_modules`. That gives Node's real types, but at Ultracite's version.
- **tsgolint's coverage is partial.** It refused the tsconfigs of zod, tRPC, Next.js and VS Code (a `types` entry that isn't installed) and Excalidraw's root tsconfig (`baseUrl` was removed in TypeScript 7). So the Oxlint/typescript-eslint comparison covers hono, Vite, Astro and Excalidraw's packages. With dependencies installed this wouldn't arise.
- **Libraries, not apps.** Seven of the eight are libraries or frameworks. App code with more I/O may float more promises.
- **The classification is judgment.** It was made by LLM raters with a written codebook, from code context and the repo files. Small repos contribute few sites (zod and tRPC 1 floating each, VS Code 6 and 2), so weighted shares are given. Perfect agreement on 20 floating sites measures codebook consistency between two Claude raters, not human judgment.
- **Some judgments rest on knowledge outside the clone.** 2 of the latent bugs (f063, f068, VS Code) depend on Monaco's factory API, which isn't in the slice.
- **History is a convenience sample.** Search terms find bugs that someone described as a missing `await` or an unhandled rejection, which skews toward the visible ones. The rule verdicts are reasoned from diffs, not run against the historical code.
- **Reported vs raw.** Repo-level config, such as Astro turning the rule off for `src`, isn't applied, because Ultracite's presets replace it. Only in-file suppressions are honoured, and there were none.

## 8. Notes on Ultracite itself

- **Preset inconsistency: `void`.** The Oxlint and ESLint presets enable `no-void` with `allowAsStatement` (comment: "Avoid conflict with typescript/no-floating-promises"; added in #618, March 2026), because `void p` is that rule's sanctioned marker. Biome's core preset enables `noVoid`, which has been on since at least Ultracite v5 (#162, June 2025). It flags `void p;` (calibration F02, F23) and has no `allowAsStatement` option. Biome's `noFloatingPromises` isn't enabled either, so Biome users get no floating-promise check, and the conventional marker for intent is an error. Raised with Hayden rather than written around.
- **Preset inconsistency: `require-await`.** Oxlint core enables ESLint's base `require-await` and turns `typescript/require-await` off, even in type-aware mode. The ESLint type-aware preset swaps base for `@typescript-eslint/require-await`, with the comment that Oxlint's base rule "is the behavioral equivalent here". It isn't on the corpus: the base rule flags 459 async functions, typescript-eslint's 227. The difference is async functions that return a promise without awaiting it (F25, F31). Combined with `return-await: always`, the fix (`return await`) satisfies both in either linter. Raised with Hayden.
- **Biome's inference rules need the config at the project root** (§3.6). That's how users normally run Biome, so it isn't a user-facing issue. It matters for anyone measuring Biome with `--config-path`.
- **History.** `@typescript-eslint/no-floating-promises`, `no-misused-promises`, `@typescript-eslint/require-await` and `no-await-in-loop` were errors in the project's first commit (`e403fb15`, 18 March 2022, the `harmony` ESLint config), with base `require-await` off, the reverse of today's Oxlint preset. No issue or commit records a specific rationale for enabling them.
