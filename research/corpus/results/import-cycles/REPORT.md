# Import cycles and barrel files in real TypeScript codebases: measurement report

The data behind the import cycles and barrel files post, measured on 2026-10-13. Generated tables are in `tables.md`. The machine-readable results are:

- `inventory.json`, `rule-census.json` and `rule-census.md`
- `graph.json`: per repo, the import graph, its cycles under six edge models, the classified cycles and Oxlint reports, barrels, fan-out and namespace imports
- `linters.json`: the calibration matrix (every message, help text and note); what each fix pass does; ESLint and Biome on the corpus, matched line by line against their models; the Oxlint fix pass on the corpus; the `prefer-export-from` export-loss check; the ESLint process-state experiment
- `sample.json` and `classifications.json`
- `history.json` and `history-lint.json`
- `decision-history.json`

The agent-experiment subjects are in `corpus/examples/import-cycles/`. Everything is regenerated by `research/corpus/scripts/import-cycles-*.cjs` (see §10).

"Import-graph rule" here means a rule that looks at how modules import each other:

- **cycles and self-imports;**
- **barrels and re-exports:** files made of `export … from`, `export *` and re-exported imports;
- **namespace imports:** `import * as ns`;
- **restricted imports and paths, dependency limits;**
- **type-only imports and exports**, which decide whether an edge exists at runtime at all.

## TL;DR

- **Corpus.** The same 8 codebases, SHAs and 3,333 files (694,309 lines) as the earlier reports. Ultracite's own CLI is listed separately; it has no cycles, barrels or namespace imports.

- **What Ultracite turns on.**
  - **Cycles:**
    - **Oxlint core:** `import/no-cycle`, with defaults `ignoreTypes: true` and an unbounded `maxDepth`.
    - **ESLint core:** `import-x/no-cycle`, with `maxDepth` ∞ and the `typescript` and `node` resolvers.
    - **Biome:** `noImportCycles` is off in core and on only in the opt-in `biome/type-aware` preset, because it needs Biome's project scanner.
    - **Self-imports:** `import/no-self-import` in Oxlint and ESLint.
  - **Barrels**, three different definitions:
    - **Oxlint `oxc/no-barrel-file`:** counts only `export *` and fires above 100 "loaded modules".
    - **Biome `noBarrelFile`:** fires on any file with a value `export … from`.
    - **ESLint `unicorn/no-barrel-files`:** fires on files made only of imports and re-exports.
    - **Re-export-all:** Biome's `noReExportAll` is off. ESLint core's `sonarjs/no-wildcard-import` reports every `export *`.
  - **Namespace imports:**
    - **Oxlint core:** nothing (`import/no-namespace` is off).
    - **ESLint core:** `import-x/no-namespace` is off, but `sonarjs/no-wildcard-import` reports every `import * as`, `import type * as`, `export *` and `export * as`.
    - **Biome:** `noNamespaceImport` reports value namespace imports.
  - **The AGENTS.md template** says "Avoid barrel files (index files that re-export everything)" and "Prefer specific imports over namespace imports".

- **Static imports put 41% of files in a cycle; runtime imports put 9.5%.**
  - **Static imports:** across 19,086 import-like statements in the measured files, counting every static import and re-export (type-only included), the 8 repos have 36 cycles (strongly connected components of 2+ files) covering 1,374 files.
  - **Type-only edges removed:** what survives TypeScript's compilation with each repo's own settings leaves 31 runtime cycles covering 316 files.
  - **No runtime cycle at all:** 24 static components have no runtime cycle inside them.
  - **Cycle sizes:** 17 of the 31 runtime cycles are two files; the largest are 102, 48 and 45 files (Excalidraw, Vite, Excalidraw).
  - **How codebases keep cycles out of runtime:** 427 `import type` statements and 12 all-inline-`type` imports sit on an edge that would otherwise close a runtime cycle.

- **Oxlint reports 996 cycles (14.3 per 10,000 lines) in 385 files, and the graph predicts every one of them.**
  - **Classified automatically**, each report's cycle path (from its note) comes out as:
    - 592 late-use (values used only inside functions; benign under ESM)
    - 190 top-level-use (a value read while a module is being evaluated)
    - 68 barrel-induced (the cycle exists only because an import goes through a re-export file)
    - 146 type-only (all in VS Code, where imports used only as types are dropped at compile time)
  - **Hand check** (50 reports, 8 per repo, two raters, weighted by repo population):
    - 58% late-use, 21% barrel-induced, 15% type-only and 6% top-level-use, once calls to function declarations that read no module state are counted as safe, which both raters' notes say.
    - Agreement: rater 1 vs rater 2 on 18 of 20 (κ 0.81), rater 1 vs automatic on 41 of 50 (κ 0.69).
    - Every top-level read in the sample is one object: Vite's `configDefaults`.

- **The three cycle rules disagree on the same code.**
  - **ESLint reports 545**, all predicted exactly by a step-by-step simulation of `import-x/no-cycle`. It reports fewer because the set of modules it has visited is shared across all imports in a file. It also follows `import()` and `export type … from`, and never reports a side-effect import.
  - **Biome (type-aware) reports 1,168.** It also reports an `import type` that sits next to a value import of the same module, and it follows `import()` and `require()`. It doesn't resolve tsconfig path aliases or `..` imports, which hides Excalidraw's cross-package cycle.
  - **Oxlint** follows neither `import()` nor `require()`, and does follow `export type * from`.
  - **Calibration:** 43 cases (§5).

- **Some cycles are real bugs, and most of them can be seen statically.**
  - **History search:** 18 merged fixes of cycle bugs in 7 of the 8 repos. In 6 of them an imported value was read during module evaluation, which surfaced as TDZ errors, `undefined` imports, a crash at startup and broken test runs.
  - **Linting each bug's files at the fix's parent commit:**
    - Oxlint and ESLint flag all 16 cycles that run through files.
    - Biome misses 3 (Excalidraw's path aliases).
    - The 2 Astro cycles run through generated virtual modules that no linter can see.
  - **One live hazard in the snapshot:** Vite's `config.ts` reads `buildEnvironmentOptionsDefaults`, `cssConfigDefaults` and `serverConfigDefaults` into a top-level object (lines 852–897) inside a 48-file runtime cycle. Issue #22634 hit it as a load-order crash when running Vite's source directly.

- **Ultracite's own fix pass changes the cycle count.**
  - **`oxlint --fix`**, which `ultracite fix` runs first, rewrites imports used only as types into `import type` (`typescript/consistent-type-imports`). On copies of the corpus that clears 171 of the 996 reports, including all 146 in VS Code, where it adds 731 `import type` lines.
  - **The other fix passes:** in calibration, `eslint --fix` and `biome check --write` do the same, and also delete unused imports, which removes cycles that never existed at runtime.

- **Barrels: common, mostly public API, and Biome's rule can't tell the difference.**
  - **Counts:**
    - 242 files contain a value re-export.
    - 176 are barrels (156 pure, 20 mostly re-exports).
    - 81 of the 176 are package entry points (68 through `exports`/`main`/`types`/`bin`, 13 through wildcard subpaths).
  - **What each rule reports:**
    - **Biome `noBarrelFile`:** 232 files, 100 of them package entry points and 59 ordinary modules with one re-export.
    - **ESLint `unicorn/no-barrel-files`:** 162.
    - **Oxlint `oxc/no-barrel-file`:** 45 (35 in raw mode). Its "N modules are loaded" adds up each `export *` subtree separately: Excalidraw's `element/src/index.ts` reports 22,287 modules and reaches 438 distinct ones.
  - **Cost.** Statically, 341 imports go through internal barrels.
    - **Median:** a consumer evaluates 7 modules through the barrel, against 5 if it imported from the declaring module (2 extra; ratio 1.4).
    - **Extra modules:** 311 of the 341 load more modules than they need.
    - **Worst cases:**
      - Excalidraw's `actions/index.ts`: 420 modules against 95.
      - Astro's `vite-plugin-astro-server/index.ts`: 303 against 2.
      - tRPC's internal `@trpc/server/index.ts`: 50 against a median of 2.
  - **Barrels in cycles:**
    - 8 of the 31 runtime cycles contain a barrel, and 12 an index file.
    - 3 runtime cycles exist only through re-exports. One is Excalidraw's `common` ↔ `math` cycle, which a source comment there names: "FIXME can't put to utils.ts rn because of circular dependency".

- **Namespace imports are mostly fine.**
  - **Counts:** 531 namespace imports, 153 of them `import type * as`.
    - Of the 378 value ones, 336 are used only through static member access (`ns.x`). 33 pass the whole object on, and 2 index it dynamically.
    - 128 import third-party modules and 39 Node built-ins.
    - Zod has 209; it's that codebase's house style.
  - **What the rules report:**
    - Biome reports exactly the 378 value ones.
    - ESLint core's `sonarjs/no-wildcard-import` reports 813 lines: all 531 namespace imports plus every `export *` and `export * as`.
    - Oxlint core reports none.

- **What a fix pass can do to exports.** `oxlint --fix-dangerously`, which `ultracite fix --unsafe` runs, applies `unicorn/prefer-export-from`'s fix, and that fix deletes names from an `export { a, b }` list.
  - **Corpus:** on copies of the corpus, one pass removes 91 exported names from 18 files in 6 repos.
  - **Worst cases:** Hono's `src/jsx/index.ts` loses 28 of its 37 exports (`useState`, `useEffect` …), and `src/jsx/dom/index.ts` loses 37.
  - **Upstream:** this is an Oxlint 1.86.0 bug.

- **Agent-experiment subjects** (§8):
  - **A (`ica`):** Astro's dev-toolbar `settings.ts` ↔ `ui-library/window.ts`, a real two-file cycle with a value read at module evaluation. Importing `window.ts` first with a toolbar placement configured throws "ReferenceError: Cannot access 'placements' before initialization".
  - **B (`icb`):** Astro's internal `core/cookies/index.ts` barrel. Biome reports it, and the right fix is in its nine importers.
  - **The constraint:** Ultracite's agent prompt allows editing only the reported file, so neither right fix is available to the agent.

## 3. Method

### 3.1 Inventory (`import-cycles-inventory.cjs`)

- **Oxlint:** `core`, `react` and `js-plugins`. Defaults come from Oxlint's `configuration_schema.json`. Whether a rule reads other modules comes from the rule sources at the `oxlint_v1.86.0` tag.
- **ESLint:** `calculateConfigForFile` on a `.ts` path (core, and core + type-aware) and a `.tsx` path (core + react), plus the `import-x/*` settings.
- **Biome:** `core` and `type-aware`, with `biome explain` for each rule's domain and options.

### 3.2 Census (`import-cycles-census.cjs` → `rule-census.cjs`)

- **What ran:** core + react + js-plugins, in both modes, focused on the 17 import-graph rules those presets enable.
- **Raw mode doesn't measure suppressions here.** Its mirror holds only the corpus files: no tsconfig, no package.json, no other files. For the module-graph rules, the gap between raw and reported is resolution.
  - `import/no-cycle`: 996 reported against 953 raw (Vite −13, Excalidraw −30).
  - `oxc/no-barrel-file`: 45 against 35.

### 3.3 The import graph (`import-cycles-graph.cjs`)

- **One TypeScript program per repo**, rooted at the measured files, with the package's tsconfig (paths included) and bundler resolution.
  - When TypeScript can't resolve an import, workspace package names are mapped through their `package.json` `exports` to source, and relative imports of `dist/` back to `src/`, as in `dead-code-exports.cjs`.
- **Every import-like statement** of every file the program loads from the clone is recorded (19,086 in the measured files), with three attributes:
  - **Kind:** `import`, `import * as`, side-effect, `export … from`, `export *`, `export * as`, `import x = require()`, `import()`, top-level `require()`, or `require()` inside a function.
  - **Type-only:** `import type`/`export type`, every specifier marked `type`, or neither.
  - **Survives:** whether the specifier is still there after `ts.transpileModule` with the repo's own `verbatimModuleSyntax` and decorator settings.
    - Without `verbatimModuleSyntax`, TypeScript, esbuild and SWC drop an import whose bindings are only used as types, or not at all.
    - With it, only `import type` and type-only specifiers go. `import { type A }` still loads the module, as `import {} from`.
- **Six edge models.** An edge is a (file, target) pair with at least one statement of the model:
  - **all:** every static statement, type-only included.
  - **oxlint:** static statements except `import type`/`export type {…}` and all-inline-type imports; `export type *` still counts. This is Oxlint 1.86.0's `import/no-cycle` with `ignoreTypes: true` (`no_cycle.rs`, `should_traverse_module`) plus calibration.
  - **eslint:** static statements plus `import()`, minus type-only imports.
  - **biome:** static statements plus `import()` and `require()`, minus type-only statements.
  - **runtime:** statements that survive compilation, plus top-level `require()`.
  - **lazy:** runtime plus `import()` and `require()` inside functions.
- **Cycles** are Tarjan's strongly connected components of 2+ files that contain a measured file.

### 3.4 Classifying cycles

Two units are classified automatically:

1. every runtime component;
2. the concrete path in the note of every Oxlint `import/no-cycle` report: the reporting file, the module it imports, and the way back.

A path's hop exists at runtime if one of its statements survives compilation. The labels, first match wins:

- **type-only:** some hop doesn't exist at runtime.
- **barrel-induced:** point every named or namespace-member import at the module that declares the name (the "debarrelled" graph). If the reporting file then no longer shares a component with what it imports, the report exists only because of re-exports.
- **top-level-use:** an import between two modules on the path (printed hop or not) is read during module evaluation, and the read is TDZ-prone.
  - **Counts as evaluation time:**
    - anywhere outside a function body
    - a class `extends`, static field or block, decorator or computed key
    - an IIFE
    - a top-level call or `new` of a local function, class or static member whose executed code uses the binding, followed through local callables
  - **Doesn't count:**
    - `class X extends LocalClass`, which runs none of `LocalClass`'s methods
    - computed keys in interfaces and type aliases, which are erased
  - **TDZ-prone means** the binding is a `let`/`const`/`class`/`enum` (or a `var`, which reads as `undefined`), or a function declaration whose body reads its own module's state or another such import. Calling a function declaration that reads nothing of the kind is safe, because it's initialised when the module is instantiated.
- **late-use:** otherwise.

For barrel-induced cycles the risk label is kept too. Runtime components get the same labels: barrel-induced if none of their files stays in a debarrelled component, otherwise top-level-use if any edge inside has a TDZ-prone top-level read.

### 3.5 The three linters, line by line (`import-cycles-linters.cjs --corpus`)

- **Oxlint** ran on each clone with Ultracite's default root config. The prediction: one report per (file, specifier) whose statements make an Oxlint-model edge inside an Oxlint-model component, at the specifier's line.
- **ESLint** ran on each clone in a fresh process started in the clone root. The prediction is a step-by-step simulation of `import-x/no-cycle` 4.17.1 (`lib/rules/no-cycle.js`, `lib/utils/export-map.js`):
  - **Which imports it checks:** every `ImportDeclaration`, `export … from`, `export *` and `import()`, in source order. An `ImportDeclaration` is skipped when it's `import type` or every specifier is `type`, which includes side-effect imports and `import {} from` (`[].every()` is true).
  - **Which edges it follows** (`ExportMap` dependencies):
    - imports, except type-only ones
    - `export … from`, even `export type`
    - `export *`, except `export type *`
    - `import()`
    - not `export * as`, which isn't captured, and not `require()`
  - **How it searches:** breadth first from the imported module, with a module-level visited `Set` that's cleared only at `Program:exit`, so every import in a file shares it.
  - **Where it reports:** the statement's first line.
- **Biome** ran on a copy of every file the graph loaded, plus every tsconfig and package.json.
  - **The prediction** is the Biome model, plus a type-only statement whenever the file also imports the same module by value statically.
  - **A missed report is explained** if the statement itself is a path-alias or `..` import, or if the file and its target fall out of the same component once only plain relative edges are kept.

### 3.6 Barrels, fan-out and namespace imports (`import-cycles-graph.cjs`)

- **Barrels.** Every file's top-level statements are counted:
  - **value re-exports:** `export … from`, `export *`, `export * as`, and imports whose bindings are only re-exported through a local `export { }`;
  - **type re-exports;**
  - **everything else.**

  The tiers:
  - **pure:** only re-exports, at least one of them a value;
  - **mostly:** at least 2 value re-exports, making up at least half the statements.

  Package entry points are every string in a package's `exports`, `main`, `module`, `types` and `bin`, mapped to source, plus Vite's build entries; wildcard subpaths are counted separately.
- **Fan-out.** For each runtime import through an internal (non-entry) barrel:
  - **via the barrel:** the repo modules evaluated, i.e. the runtime closure from the barrel;
  - **direct:** the union of the closures from the modules that declare the imported names, found with the checker. A namespace import counts if its members are only read statically.

  This is a static stand-in for what a dev server, test runner or Node evaluates; bundlers with `sideEffects: false` can drop unused re-exports. Third-party modules aren't counted.
- **`oxc/no-barrel-file`:** the count is predicted from the rule's source (for each `export *`, 1 plus the modules its target loads, summed over the file), with distinct modules reported alongside.
- **Namespace imports** are classified by how the binding is used (static member access, type positions, dynamic indexing, or the whole object escaping) and by target (internal, workspace, third-party, Node built-in).

### 3.7 Calibration (`calibration/import-cycles/`, `--calibration --autofix`)

- **43 cases**, one directory each so they can't reach each other: 24 cycle cases, 11 barrel cases and 8 namespace files.
- **Configurations:**
  - Oxlint core + react, and with js-plugins
  - ESLint core, and core + react
  - Biome core + type-aware, and core alone
- **Recorded:** every message, Oxlint help and note, and Biome's terminal advice.
- **`--autofix`** runs each fix pass `ultracite fix` uses on copies (`oxlint --fix` and `--fix-dangerously`, `eslint --fix`, `biome check --write` with and without `--unsafe`), then re-lints the cycle cases with the same linter.

### 3.8 Hand classification (`import-cycles-sample.cjs`)

- **Population:** the 996 Oxlint reports.
- **Sample:** seed 20261013, up to 8 per repo, frozen in `sample.json`. That's 50 reports: Zod 2, tRPC 0, 8 each from the rest.
- **Worksheet:** each cycle path with every hop's import lines and permalinks, without the automatic label.
- **Codebook** (in `sample.json`):
  - **labels:** type-only, barrel-induced (with its risk), top-level-use, late-use, unclear;
  - **the right fix:** `import type`, import directly, extract a module, move code, lazy import, leave it, other.
- **Raters:**
  - **Rater 1,** a Claude subagent with read-only access to the clones, labelled all 50.
  - **Rater 2,** a separate Claude subagent, labelled a seeded blind subset of 20 without the automatic labels or rater 1's.
  - Both are Claude models, so agreement measures how consistently the codebook applies.

### 3.9 History (`history.json`, `import-cycles-history.cjs`)

- **Search.** A Claude subagent searched the 8 upstream repos with `gh`: 116 searches, each logged with its hit count. The terms covered:
  - circular or cyclic dependencies and imports
  - TDZ and "before initialization"
  - "is not a constructor" and "extends value undefined"
  - barrels, re-exports, `export *` and `optimizePackageImports`
  - import and evaluation order, lazy and dynamic imports
- **Selection.** A fix counts as a bug only if it was merged and its cycle could be confirmed in the parent commit's files. The rest are under `unverified` and `rejected`. 31 fixes to how Vite or Next.js handle cycles in user code are listed separately.
- **Lint.** `import-cycles-history.cjs` downloads each cycle's files at the fix's parent commit, plus any tsconfig its aliases need, and lints them with all three cycle rules.

A Claude subagent ran `git log -S` on every rule name and template line, and read the changelog, changesets, docs, and the `gh` issues and PRs on haydenbleasel/ultracite (§9).

**What each cycle rule needs:**

- **Oxlint** needs its module resolver. It skips `node_modules`, finds each file's nearest tsconfig, and maps `.js` to `.ts`.
- **ESLint** needs `eslint-import-resolver-typescript` loadable from the project directory. Without it the rule resolves nothing and reports nothing, with no warning (checked by linting a calibration copy outside the repo). The preset also names a `node` resolver whose package isn't installed.
- **Biome** needs its project scanner, with the config at the root of the linted tree.

### 4.5 The same rule in three linters

| | Oxlint | ESLint | Biome (type-aware) |
| --- | ---: | ---: | ---: |
| reports on the corpus | 996 | 545 | 1,168 |
| predicted by its model | 996 | 545 | 1,213 |
| matched | 996 | 545 | 1,168 |
| missed, all explained | – | – | 45: path aliases Biome doesn't resolve (Excalidraw's `@excalidraw/*`, 41) and `..` imports in Vite (4) |

Why they differ:

- **ESLint's search is shared across a file's imports.** An import whose way back runs through modules an earlier import already explored isn't reported. For example, VS Code's `lineTokens.ts` imports `../languages.js` on line 6 and `../model.js` on line 9; both close cycles, and ESLint reports line 6 only. The simulation reproduces every count.
- **ESLint reports on the statement's first line**; Oxlint reports on the specifier's.
- **ESLint follows `export type {…} from`.** Those are its only two reports in tRPC, which has no runtime cycle.
- **ESLint follows `import()`.** Calibration cases c10 and c20 are cycles that a dynamic import breaks at runtime, and ESLint reports them.
- **ESLint never reports a side-effect import**, and doesn't follow `export * as`.
- **Biome reports the `import type` line next to a value import of the same module:** 2 extra lines in Zod and 5 in Hono.
- **Biome follows `require()` and `import()`.** That's why it reports 201 lines in Next.js against Oxlint's 87.
- **Biome doesn't resolve `..` imports, or tsconfig `paths` that a package's tsconfig inherits through `extends`.** Calibration c14 (aliases in a nested tsconfig) and c24 (`..`) show both.
- **Oxlint ignores `import()` and `require()`, follows `export type * from` (c21), and resolves aliases from each file's nearest tsconfig (c14).** ESLint and Biome both miss c14.

**ESLint depends on process state.** Linting Zod and then Excalidraw in one process gives 222 Excalidraw reports; a fresh process gives 241. The resolver's caches outlive the change of directory. Linting a subset of Excalidraw first doesn't change its count.

## 6. Findings worth stating carefully

- **Most cycles a linter reports exist at runtime, and most of those are harmless under ESM.**
  - 85% of Oxlint's reports are runtime cycles (all but VS Code's), and about three in five reports are late-use, by the automatic labels and by the hand sample.
  - The hazard is an evaluation-time read of a TDZ-prone binding. That's 6% of reports in the weighted sample, 19% by the automatic label (mostly Vite and Excalidraw), and 3 of the 31 runtime cycles.
  - Whether such a read throws depends on import order. Subject A ships fine because Astro's entry point imports the safe file first.
- **Type-only imports are the biggest difference between a static cycle and a runtime one, and the linters handle them differently.**
  - All three skip `import type`.
  - All three skipped `import { type A }` (c07), even though Biome's docs say it doesn't.
  - None knows that a plain import used only as a type is dropped at compile time.
  - Ultracite's own fix pass converts those imports, so after `ultracite fix` the type-only reports disappear.
- **Linter cycle counts can't be compared across linters.** The same corpus gives 996, 545 and 1,168. Each count is reproducible from its linter's traversal rules, and none of them counts cycles.
- **A barrel rule that fires on package entry points can't be followed literally.** 100 of Biome's 232 reports are a package's public entry, and agents are told to fix the reported file and not suppress.
- **Internal barrels cost little at the median, with a long tail.** The median is 2 extra modules; the worst is 325.

## 7. Caveats

- **Snapshot.** The repos are at their 2026-10-10 HEADs. Next.js is 40% of the source lines.
- **Sparse clones.** VS Code's slice can't show cycles through `src/vs/base` or `platform`, and its 146 reports cover the editor/common slice only. Next.js's package entry points are outside its clone.
- **Static analysis.**
  - The runtime model is TypeScript's elision with each repo's settings. Bundler and SWC configurations can differ.
  - Fan-out counts only repo modules, from static edges. It isn't a timing.
- **The top-level detector** uses the syntax tree and the checker. It follows local functions and classes, but not calls into other modules, so it can miss indirect top-level reads. It marks a risk, not a crash.
- **The classification is judgment** by Claude raters with a codebook, on a sample of 50 (none from tRPC). The barrel test can be read at the level of the path or of the report; both are reported.
- **History is a convenience sample** limited by search terms. Each bug's files were linted on their own, not in the full repo.
- **Biome's corpus run** used a dedicated config with Ultracite's severities, because the presets' file includes would apply to the copies' paths.

  - **VS Code's `chatToolInvocationPart` ↔ `chatToolConfirmationSubPart`,** at the parent of a783943: a `class … extends BaseChatToolInvocationSubPart` at module evaluation, fixed by extracting the base class.

## 9. Notes on Ultracite itself

These are raised for Hayden, not fixed.

1. **The agent prompt forbids the fix the cycle rule's help recommends.**
   - Oxlint's help says "Consider extracting shared code into a separate module that both files can import".
   - `ultracite fix --claude/--codex` says "Edit only the file above. Do not create, delete, or modify any other file."
   - Barrels have the same problem: their right fix is in the importers. Expect evasions; subjects A and B are built to measure them.
2. **`ultracite fix --unsafe` with Oxlint can delete exports.**
   - `unicorn/prefer-export-from`'s dangerous fix (Oxlint 1.86.0) rewrites `import { a } …; import { b } …; export { a, b }` to `export { a } from …` and drops `b`.
   - On copies of the corpus it removes 91 exported names from 18 files, 28 of them from Hono's `jsx/index.ts`.
   - This is an upstream bug to report.
3. **Namespace imports are treated three ways.**
   - **Oxlint core** allows them.
   - **ESLint core** reports every one, `import type * as` included, through `sonarjs/no-wildcard-import`. Meanwhile `import-x/no-namespace` is off, and `import-x/prefer-namespace-import` is on but inert.
   - **Biome** reports the value ones.
   - **The agent template** says to prefer specific imports.
   - The same sonarjs rule also reports every `export *` (part of its 813 corpus lines), while Biome's `noReExportAll` is off.
4. **"Barrel" means three things.**
   - **`oxc/no-barrel-file`:** only past 100 `export *` modules (45 hits).
   - **Biome `noBarrelFile`:** any value `export … from` (232).
   - **ESLint `unicorn/no-barrel-files`:** files that only re-export (162). It arrived unannounced with the unicorn 73 bump.

   The parity script skips `oxc/*`. Biome and ESLint both fire on package entry points, which are the public API.
5. **`noImportCycles` is only in Biome's type-aware preset, while Oxlint and ESLint run their cycle rules in core.**
   - **Docs:** `configuration.mdx` L41 says rules that scan the whole project stay out of core, which doesn't describe Oxlint or ESLint.
   - **The recorded reason was scanner cost** (v5: "too slow"; #324: 300 ms against 13 s).
   - **Later measurements point the other way:** #843 put core plus the whole type-aware preset at 915 ms against 864 ms for core alone, and `noUndeclaredDependencies`, also a project rule, moved into core. Biome's corpus run here took 0.1–0.6 s per repo with the scanner on.
6. **ESLint's `import-x/no-cycle` underreports, depends on process state, and can fail silently.**
   - It reports 545 where Oxlint reports 996, by design of its shared visited set.
   - In one process, a project linted earlier lowers the count (241 → 222).
   - With no loadable `eslint-import-resolver-typescript`, it reports nothing and prints no warning.
   - The preset also names a `node` resolver that isn't installed.
7. **ESLint core turns on `import-x/dynamic-import-chunkname`,** a webpack magic-comment rule, through the every-rule policy. It fires 188 times on the corpus and has no Oxlint counterpart.
8. **Some rules are on and inert:** `no-restricted-imports` (Oxlint, ESLint), `noRestrictedImports` (Biome), and `import-x/no-restricted-paths` and `import-x/prefer-namespace-import` (ESLint) have no options, so they can't report anything.
9. **Type-only edges.**
   - Oxlint follows `export type * from`, and ESLint follows `export type { … } from` (calibration c21, c23). Both are erased at compile time; ESLint's two tRPC reports are this.
   - None of the rules knows that a plain import used only as a type is dropped. All 146 VS Code reports are this. Ultracite's own `oxlint --fix` clears them.
10. **Biome's cycle rule doesn't resolve `paths` inherited through tsconfig `extends`, or `..` imports.** It misses Excalidraw's cross-package `common` ↔ `math` cycle (41 reports), the one a source comment there mentions.
11. **The agent template once said "Prevent import cycles."** (2025-06-22 to 2025-10-20) and now says nothing about cycles, while two of the three linters enforce them in core. The barrel and namespace lines have no recorded rationale.
