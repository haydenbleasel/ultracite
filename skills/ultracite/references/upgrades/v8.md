# Upgrading to Ultracite v8

Ultracite v8 stops running Prettier inside ESLint and Stylelint, moves the Cypress and Storybook rules and the type-checked rules out of the ESLint core preset into presets of their own, and turns on Oxlint's type-aware linting when `oxlint-tsgolint` is installed. `ultracite init` also has a `--yes` flag for skipping prompts, which `--quiet` no longer does.

## Does the project need it?

Yes, if any of these is true:

- An ESLint config (`eslint.config.*`) or Stylelint config (`stylelint.config.*`, `.stylelintrc*`) sets the `prettier/prettier` rule.
- The project uses ESLint with Ultracite's presets, depends on `cypress`, and its ESLint config doesn't import `ultracite/eslint/cypress`.
- The project uses ESLint with Ultracite's presets, depends on `storybook` or an `@storybook/*` package, and its ESLint config doesn't import `ultracite/eslint/storybook`.
- The project uses ESLint with Ultracite's presets, its ESLint config sets one of the rules under [Rules that need type information](#rules-that-need-type-information) to anything other than `"off"`, and it doesn't import `ultracite/eslint/type-aware` or set `parserOptions.projectService` itself.
- The project uses Oxlint, has `oxlint-tsgolint` in its dependencies, and its Oxlint config (`oxlint.config.ts`, `oxlint.config.mts` or `.oxlintrc.json`) doesn't set `typeAware: true` in `options`.
- The project uses ESLint with Ultracite's presets, and `.zed/settings.json` formats a language with the `eslint` language server: `"formatter": { "language_server": { "name": "eslint" } }`, on its own or in a list.
- Something runs `ultracite init` with `--quiet` but without `--yes` (or `-y`): a `package.json` script or a CI workflow in `.github/workflows/`.

## Steps

1. Remove every `prettier/prettier` entry from the ESLint and Stylelint configs. v8 doesn't load `eslint-plugin-prettier` or `stylelint-prettier`, so ESLint and Stylelint would stop with an unknown rule. Prettier still checks and formats every file, as its own step of `ultracite check` and `fix`. Leave the rest of each `rules` object as it is.

2. If the project depends on `cypress`, import Ultracite's Cypress preset in the ESLint config and spread it after `core`, in the same style as the presets already there. Do the same with `ultracite/eslint/storybook` if the project depends on `storybook` or an `@storybook/*` package. v7 applied both rule sets from the core preset.

   ```js title="eslint.config.mjs"
   import core from "ultracite/eslint/core";
   import cypress from "ultracite/eslint/cypress";
   import react from "ultracite/eslint/react";
   import storybook from "ultracite/eslint/storybook";

   export default [...core, ...react, ...cypress, ...storybook];
   ```

3. If the ESLint config sets one of the rules under [Rules that need type information](#rules-that-need-type-information) to anything other than `"off"`, and doesn't set `parserOptions.projectService` itself, import `ultracite/eslint/type-aware` and spread it after `core`, and for each of the `angular`, `jest`, `nestjs`, `qwik`, `tanstack` and `vitest` presets the config imports, import its add-on, `ultracite/eslint/<framework>/type-aware`, and spread it right after that preset. v7's core preset gave every TypeScript file type information, so the project relied on it. Without the type-aware preset, most of these rules stop ESLint with "You have used a rule which requires type information", and the SonarJS and Unicorn ones report nothing. Keep the project's own setting for each rule.

   ```js title="eslint.config.mjs"
   import core from "ultracite/eslint/core";
   import typeAware from "ultracite/eslint/type-aware";
   import vitest from "ultracite/eslint/vitest";
   import vitestTypeAware from "ultracite/eslint/vitest/type-aware";

   export default [...core, ...typeAware, ...vitest, ...vitestTypeAware];
   ```

4. If the project uses Oxlint and has `oxlint-tsgolint` installed, add `typeAware: true` to `options` in the root Oxlint config, creating `options` when the config has none. v7 installed `oxlint-tsgolint` for `init --type-aware` without turning it on. If a `package.json` script passes `--type-aware` to `ultracite check` or `fix`, it can stay.

   ```ts title="oxlint.config.ts"
   export default defineConfig({
     env: core.env,
     extends: [core],
     ignorePatterns: core.ignorePatterns,
     options: { typeAware: true },
   });
   ```

5. Wherever `ultracite init` runs with `--quiet` and without `--yes`, add `--yes`. In v8, `--quiet` only hides progress output and no longer skips the prompts. Keep `--quiet` and every other flag.

6. In `.zed/settings.json`, change every `formatter` that names the `eslint` language server to `"prettier"`, and leave the `code_actions_on_format` next to it as it is. v7 ran Prettier as an ESLint rule, so ESLint's language server formatted too. In v8, Zed's Prettier integration formats after ESLint's fixes, with the project's own Prettier config and plugins.

   ```jsonc title=".zed/settings.json"
   "TypeScript": {
     "code_actions_on_format": {
       "source.fixAll.eslint": true,
       "source.organizeImports.eslint": true,
     },
     // v7: "formatter": { "language_server": { "name": "eslint" } }
     "formatter": "prettier",
   }
   ```

7. Apart from step 3, don't add `ultracite/eslint/type-aware`. v8 runs ESLint's type-checked rules only in projects that ask for them, with `npx ultracite init --type-aware`, and unless the config already sets one of those rules, that's the user's choice to make, not part of the upgrade.

The Git hooks (Husky, Lefthook, pre-commit) and agent hooks v7 wrote keep working. Re-running `npx ultracite init` with the same `--integrations` and `--hooks` updates them to fix only the staged files and to run the installed `ultracite` directly; that's for the user to run, not part of this guide.

## Check

`npx ultracite doctor` passes, and `npx ultracite check` runs without a configuration error.
